# 上篇：我们如何做到的

## 第一章 起点：为什么它是"网关"而不是"聊天软件"

### 1.1 名字里藏着的第一性原理

项目叫 `agent_gateway`。这个名字不是随便起的，它定义了整个系统的生态位：

**网关 = 一座门，不是一栋楼。**

普通开发者想"做一个 AI 聊天应用"，会直接写对话逻辑。但你没有——你决定让所有流量**必须经过这道门**。这个站位让后面所有能力都有了落脚点：

- 用户不直连 DeepSeek，而是先过网关 → 网关才能"验身份、计量、拦截、记账、观测"
- 认证、限流、熔断、缓存、计费、监控，全部"长在门上"，而不是"后焊在聊天功能上"

这就是为什么后来你能加支付系统、能加多实例、能加熔断——因为"门"的天性里天然带着这些位置，你只是把预留的位置填上了。

### 1.2 设计前的三个自问

写任何代码之前，这套系统只回答了三句话：

1. **它站在哪里？** 站在用户和模型之间。边界：外网 → Nginx → 网关 → DeepSeek / PostgreSQL / Redis。
2. **它管什么？** 管"请求怎么进出"，不管"回答说什么"。回答是 Agent 的事。
3. **它不管什么？** 克制。网关不自己写业务逻辑、不存业务数据（支付独立成 `app/payment/`）。

**反例对比**：很多人先让聊天跑通，再补登录、再补限流、再补监控——每一步都是后焊的补丁，系统长成违章建筑。你第一步定了"我是门"，后面所有器官都是同一条脊柱上长出来的。

### 1.3 第一行代码的隐喻

`main.py` 里最先创建的表是 `requests`（请求跟踪），字段包括 `first_token_time`（首 token 时间）。这看起来只是监控字段，实际是网关的"心跳"——流式对话里，用户等多久看到第一个字，是系统的生命体征。**你在第一天就埋下了传感器。**

## 第二章 骨架期：让一次请求完整跑通

### 2.1 主链路（纵向打通）

设计师的第一原则：**先纵后横**。先让"用户 → 登录 → 聊天 → 流式返回"这一条链路完整跑通，再横向加厚。

- 技术底座：FastAPI + uvicorn + asyncpg（异步 PostgreSQL 驱动）+ Redis
- 流式输出：SSE，逐字把答案推给前端，用户有"打字机"体验
- 请求跟踪：每次请求记录开始/首token/结束时间、模型、状态——这就是最早的"可观测"

### 2.2 数据库选择：SQLite → PostgreSQL 的迁移

项目早期用 SQLite，后来迁移到 PostgreSQL。为什么必须迁：

- SQLite 是单机文件库，扛不住并发写，没有连接池
- PostgreSQL 支持连接池（asyncpg min=20 max=50）、JSONB、全文检索、向量扩展（pgvector）、模糊匹配扩展（pg_trgm）

这次迁移也定下了规矩：**数据库连接串必须从环境变量注入，不写死在代码里**（后来成为密钥治理的源头）。

### 2.3 配置外置

密钥和配置全部从代码剥离：

- `app/core/config.py` 用 `os.getenv()` 读取
- `.env` 文件（gitignored）存真实密钥
- 容器通过 docker-compose 的 `env_file` 注入

原则：**同一份代码，不同环境用不同配置跑。**

## 第三章 能力期：让系统"会思考"

### 3.1 意图路由：不是所有问题都值得大动干戈

系统收到的每个问题，先过一道"路由器"判断：

- **简单问题**（查天气、查酒店）→ 只调 1 个 Agent + 1 次 LLM，秒回
- **复杂问题**（规划行程）→ 进多 Agent 圆桌
- **推荐问题**（"帮我规划攻略"）→ 4 个领域 Agent 全上

分类用两层：关键词匹配（零成本、毫秒级）→ LLM 轻量分类（边界情况兜底，只花 100 token）。

**价值**：简单问题不为复杂流程空转，省 token 又省延迟；复杂问题有足够深度。

### 3.2 多 Agent 圆桌：让专家开会

复杂任务不是让一个 Agent 硬答，而是让 4 个领域专家协作，三阶段协议：

```
Phase 1 并行工具调用   每个 Agent 查自己的数据（天气/酒店/路线/美食）
Phase 2 并行思考分析   每个 Agent 看到所有结果后发表意见
Phase 3 交叉审阅       Agent 互相补充、纠错、跨领域建议
Final  主 Agent 综合   把讨论结果整理成一份完整回答
```

并行用 `asyncio.gather`。为了控制成本，工具结果会压缩成"找到 5 家酒店"这类一句话，防止讨论上下文爆炸。

### 3.3 三级语义缓存：让重复问题不重复花钱

用户 1000 次问"离婚财产怎么分"，可能有 500 种问法但意思相同。语义缓存让系统"记得"答过类似问题：

- **L0 进程内 LRU**（256 条）：微秒级，本实例内存
- **L1 精确匹配**：sha256 哈希，毫秒级
- **L2 语义匹配**：PostgreSQL pg_trgm 相似度 > 0.85 才算命中

命中后逐级回填，越用越快。阈值调到 0.85 的原则：**宁可不命中，不要命中错的**。

**关键：缓存带上下文维度**（`cache_ctx` = 人格|位置|画像指纹的组合键）。A 用户的个性化回答（按位置/画像推荐）**不会被 B 用户命中**——否则会跨用户泄个性化内容。这是防"缓存串号"的隔离设计，画像用 SHA-256 前 8 位做指纹参与键，既隔离又不重。

### 3.4 冷热分层记忆：让 LLM 有记忆

LLM 本身无状态，每次调用都要带上历史。记忆按冷热分两层：

- **热层 Redis**：最近对话，毫秒取回，1 小时 TTL
- **冷层 PostgreSQL**：长期记忆，永久保存

读写分离 + 异步落盘：先写 Redis（立即生效），再异步写 PG。**关键设计**：PG 写入用信号量限流（最多 5 并发），防止高并发下数据库写入占满连接池、拖垮主流程。

### 3.5 人格系统：一核双用、可插拔

系统能承载多个人格（旅行 / 民法典），靠的是**引擎与业务分离**：

- 引擎只做：决定下一步动作（调工具 or 直接回答）、流式输出
- 人格 = 配置包：人设 Prompt（`prompts/*.json`）、工具注册表、模型策略

新增一个领域 = 新增一个配置包，核心代码零改动。这就是简历里"一核双用、可插拔"的真正含义。

## 第四章 治理期：让系统敢上线

### 4.1 安全审计：24 项修复

上线前做了一次系统审计，修复了 24 项风险。最关键的几项：

| 风险 | 修复 |
|---|---|
| 默认 JWT 密钥 | 未配置则启动直接报错（fail loudly） |
| CORS 过宽 | 收紧为 localhost 白名单 |
| 上传目录可直访 | 移除静态挂载 |
| LLM 注入 | Agent 上下文与上传内容都做指令注入过滤 |
| 熔断器全局单例 | 改为按端点隔离的注册表模式 |
| 日志泄露用户查询 | 移除含原始查询的日志 |

原则：**安全不是后焊的，是从审计中长出来的抗体。**

### 4.2 限流：四维防护

按用户 + 角色（admin/user）分档，四个维度：

- **QPS**：滑动窗口（Redis 服务端 `TIME` 决定当前/前一秒两个计数器，按已过比例加权估算，Lua 原子；用服务端时间摆脱客户端时钟漂移）
- **并发**：同时进行中的请求数（Lua 原子"检查+增量"，超限不占位；30 秒超时自释放防槽位泄漏）
- **日请求数**：跨零点自动重置
- **日 token 数**：成本兜底（token = 钱）

全部基于 Redis 原子 Lua 脚本，因为 4 个实例共享一个 Redis，计数才能全局一致。

### 4.3 熔断：防雪崩

下游（DeepSeek）连续失败时，如果所有请求都傻等超时，连接池会被占满，整个网关假死。熔断器用三态状态机解决：

```
CLOSED（正常）--3次失败--> OPEN（熔断，秒拒）--30秒--> HALF_OPEN（试探）--成功--> CLOSED
```

按端点隔离（注册表模式）：一个接口挂了只熔断它自己，不拖垮全局。

### 4.4 法律映射表：模型级问题的架构解法

一个典型案例：DeepSeek 模型总是把"七天无理由退货"错误归因到民法典（模型训练数据的顽固行为），改 prompt 无效。架构解法：

- 建一个**法律依据纠正映射表**（`law_mapping.py`）：命中"七天无理由退货"→ 直接引导到《消费者权益保护法》
- 在调用 LLM 之前先查映射表，命中则直接返回引导信息

结果：CC019 用例从 2 分提到 7 分。**这个故事的面试价值极高：说明你懂得"模型解决不了的问题，用架构手段绕过"。**

### 4.5 测评：用数据证明"能用"

- 190 条法条级人工标注问答集，按 train / holdout 切分；20 条快速门禁用例，发布前跑 holdout 45 条
- 早期另有"民法典专项 60 条平均 8.95/10"的说法，因无原始打分明细可查，已不再引用
- 检索质量（重排开启，自测）：holdout Recall@5 93.0%、Recall@10 99.3%、MRR 0.879
- 未做对外可复现的负载压测，容量以内存上限与告警阈值为约束

原则：**业余者"觉得能用"，设计师用数据证明能用。**

## 第五章 商业化：让系统值钱

### 5.1 模拟支付体系

系统有了真实成本（DeepSeek token），就必须能计费。支付系统是完整的"迷你金融系统"：

- **钱包**：余额、冻结、总充值/消费/退款
- **订单**：完整状态机（pending → paid → completed/failed/refunded）
- **渠道**：余额 100% / 支付宝 95% / 微信 95%（模拟真实失败率）
- **发票**、**每日对账**
- **交易流水（WAL）**：只追加、不可篡改，流水 = 真相

扣费规则：10 元 / 万 token，对话完成后异步扣费，余额不足不阻塞对话。

### 5.2 并发安全：双锁

资金操作最怕并发，用两层保险：

- **分布式锁**（Redis SET NX EX）：防止多实例同时操作同一钱包——锁管"同时进门"
- **乐观锁**（version 字段）：更新时校验版本号，冲突则重试——version 管"数据一致"

## 第六章 工程化：让系统可持续

### 6.1 Git 与密钥治理

项目最初连版本控制都没有。建立过程：

1. `git init` + 基线提交
2. **密钥扫描发现 41 个文件硬编码了密钥**（DeepSeek Key、数据库密码、admin 密码）
3. 新建 `_env.py`（零依赖 .env 读取器），40+ 脚本全部改为从 `.env` 读取
4. `config.py` 移除数据库密码默认值（fail loudly）
5. `.gitignore` / `.dockerignore` 排除密钥、数据、备份、本地产物

**为什么重要**：密钥一旦进 git 历史就永久存在，无法清除，所以提交前必须扫描。

### 6.2 CI/CD 流水线（ci.sh）

把"部署"从手动命令变成自动流水线，五阶段：

```
[1] 语法检查（AST 解析，不写文件）
[2] 构建镜像（层缓存，commit SHA 打标签）
[3] 滚动部署（一次只升级一个实例，健康后再动下一个）
[4] 冒烟测试（nginx /health + 登录链路）
[5] 完成；任何一步失败自动回滚到上个镜像
```

**滚动发布的价值**：旧方式 4 个实例同时重建 = 上线瞬间全挂；滚动发布 = 服务不中断。

> 现状说明：ci.sh 的语法/AST 门禁 + 单测**确实在每次代码变更前跑**（`check_code_rules` 硬闸）。而"5 阶段滚动发布"描述的是**多实例全栈**的发布设计；当前公网实际跑的是**单实例精简版（lite）**，发布走 `build + up`（本轮进一步改为**本地构建镜像 + docker save/load 传服务器**，避免低配实例 build 拖垮服务）。两条路径按部署规模选。

### 6.3 数据库迁移（Alembic）

建表曾经靠 `CREATE TABLE IF NOT EXISTS` 手动脚本，线上库结构改起来没有版本记录。Alembic 解决：

- 基线迁移把 13 张表 + 扩展 + 索引完整固化
- 表结构变更像代码一样有版本号、可追溯、可回滚
- 线上库已 `stamp` 到基线版本，今后新表/新列都走迁移

### 6.4 SLO 与告警

用数字定义"健康"：

- 错误率 < 1%、p95 延迟 < 5s、缓存命中率 > 30%
- 9 条自动告警（错误率 / 流量骤降 / 慢请求 / token 突增 / 缓存命中率 / 支付失败 / 下游故障 / 实例宕机）

**容量约束**：compose 网关最多 4 实例，增减由脚本按 CPU 阈值触发；生产是 2 核 1GB 单机，只跑 1 实例 lite 栈。未做负载压测。

### 6.5 安全加固与运维自动化

- **nginx WAF**：SQL 注入 / XSS / 路径穿越特征 → 直接 403，不打到后端
- **数据保留**：对话 90 天、请求 30 天、流水 365 天，自动清理防止库无限增长
- **备份恢复演练**：恢复到临时库校验行数，验证"备份真的能恢复"
- **弹性伸缩**：运行时加/减实例，nginx 热更新
- **HTTPS**：Cloudflare 隧道提供公网 HTTPS（免费），无需自购证书

### 6.6 环境大坑：wslrelay 拦截 5432

Windows + Docker Desktop (WSL2) 环境的隐藏坑：

- `localhost:5432` 被 `wslrelay.exe`（监听 127.0.0.1）拦截 → 认证失败
- postgres 容器 IP 从 Windows 宿主不可达（WSL2 桥接限制）
- **可靠路径：局域网 IP**（命中 `com.docker.backend` 的 0.0.0.0:5432 监听）

解决方案：`migrate.py` 自动探测主机（DB_HOST > localhost > 局域网 IP）。

## 第八章（2026-08-31 收尾）架构演进：超长文件模块化重构

系统上线后"能跑"，但三个核心文件长成了**上帝文件**，违背工程红线（文件≤600 行 / 函数≤80 行）。这一章讲这次"从能用到可维护"的重构——**这是简历里最能体现工程素养的一段**。

### 8.1 为什么要重构
| 文件 | 重构前 | 问题 |
|---|---|---|
| `app/main.py` | 1076 行 | 内联大量路由 handler（含 ~66 行 GitHub callback 等），路由/接线/生命周期混杂 |
| `app/payment/service.py` | 1193 行 | `process_recharge` 135 行 / `deduct_token_cost` 120 行（资金上帝函数） |
| `app/routes/v2.py` | 1848 行 | `chat_stream_v2` 近千行 + 内嵌 `generate` 951 行（流式闭包上帝函数） |

长函数的代价：改一处要通读几百行、多子页面冲突大、"改完不知道影响谁"。**债不过夜**——写完立即检查，超限当场收敛。

> **重构状态（2026-09-02）**：`app/routes/v2.py` 已由 1848 行拆为 **135 行路由薄壳**，`generate` 闭包逻辑下沉至 `app/services/`（chat_stream_core / chat_react / chat_fast_paths / chat_stream_ctx / llm_streaming / chat_fallback / chat_support / file_upload / agent_tasks / reasoning_guard），本表为**重构前**基线。

### 8.2 重构纪律（这次很讲究）
- **纯移动、行为等价**：只搬家不改逻辑。每个 handler/函数原样搬入新模块，公开面（路由/符号）re-export 保留，**行为零变化**。
- **每步验证**：每拆一步跑 `import 冒烟 + 单测 40/40 + AST 门禁 + OpenAPI 路由集比对`，确认无行为位移再进下一步。
- **安全边界**：资金事务/锁块、流式生成器闭包流——这两个是"运行期才暴露错误、离线测不到"的高风险区，**不擅动**，只拆确认安全的纯缝。

### 8.3 各文件怎么拆的
| 文件 | 重构后 | 手法 |
|---|---|---|
| `main.py` → **354 行** | 拆出 6 路由模块（auth/phone/oauth/users/conversation/observability）+ `core/otel.py`（OTEL 可用性单一权威源）；main 只留接线/生命周期/中间件 |
| `service.py` → **581 行** | 删死 DDL（Alembic 接管）+ 资金函数拆纯缝 + 分三成 `_ledger.py`(账本原语)/`query.py`(只读)，公开面 re-export 保留 |
| `v2.py` | 抽 `_finalize_answer`（6 处重复 finalize 尾统一）、`_route_intent`（意图路由）、`_record_token_usage`（Token 计量）；`generate` 951→**890** |

**关键取舍**：`process_recharge`(88)/`deduct_token_cost`(114) 仍 >80 行——因**保留事务原子性**，不强行拆分（刷行数或破坏事务都不诚实）。这是"知道哪些能拆、哪些不能拆"的架构判断。

### 8.4 本轮顺带修复
- **测试门禁**：`conftest` 补 `APP_ENV=test`（此前全部测试无法收集）、`check_qps` 恢复 `_now` 注入（测试漂移）、锁测试补丁目标对齐拆分后模块 → 单测 40/40 全绿。
- **定位体验（真用户痛点）**：iploc 对私有/保留 IP 返回空（不再拿"局域网"占位当城市）；地图页**授权定位后总是尝试浏览器定位**，不再被 `showPrompt` 路径跳过——解决"用户信任授权了却被要求手输"。
- **密钥补齐**：从运行容器提取真实 AMAP/DEEPSEEK key 注入 `/deploy/.env.lite`，天气/聊天真正可用。

### 8.5 一个真场景才暴露的"坑"
重构时把 `_finalize_answer` 插到了 `@router.post("/chat/stream")` 装饰器与 `chat_stream_v2` 之间 → **装饰器误绑到 helper**，`/v2/chat/stream` 校验的 body 变成 `mm/query/answer/cache_ctx/...`，chat_stream_v2 失去路由。**import / 单测测不出，真实 POST /chat/stream 立刻暴露**。教训：**抽 helper 时勿把 async def 放在装饰器与 handler 之间**（放安全区：既有 handler 之后、下一个装饰器之前）。

### 8.6 价值（面试可讲）
- **敢重构、会重构**：不是把代码写大，而是把大的拆小、拆清晰，保持行为等价。
- **架构判断力**：知道纯缝该拆、事务/流式边界不能拆；敢于对"资金函数仍 >80 行"做诚实取舍。
- **验证纪律**：拆 1000 行也全程绿（单测/门禁/路由集/真栈回归），不是嘴上重构。
- **真实回归**：本地建隔离栈 + 云端干净重装上线（用"本地构建镜像 + docker save/load 传服务器"，避开低配实例 build 拖垮服务），新代码已上线公网。

# 下篇：核心概念逐个拆解

> 每个概念按统一格式：**是什么 → 为什么需要 → 本项目怎么实现 → 去掉会怎样**。

## 1. 认证（Authentication）

**是什么**：证明"你是谁"的系统机制。

**为什么需要**：网关是门，门必须验身份。没有认证，任何人都能烧你的 token（钱）、读别人的数据。

**本项目实现**（四层防线）：
1. 密码 bcrypt 哈希存储（数据库被拖库也拿不到明文）
2. 登录成功发 JWT（无状态票据，HS256 签名，含过期时间）
3. FastAPI 依赖注入（`Depends(get_current_user)`，验不过直接 401）
4. 多种进门方式：密码 / GitHub OAuth / 手机号 + 短信验证码

**去掉会怎样**：限流、记忆、支付全部失效——因为系统不知道"谁"在请求。

## 2. 限流（Rate Limiting）

**是什么**：控制"每个用户一段时间内能用多少资源"。

**为什么需要**：防滥用、防单用户占满资源、成本控制（token = 钱）、公平性（角色分级）。

**本项目实现**：Redis 原子计数器实现四维限制（QPS / 并发 / 日请求 / 日 token），admin 与 user 分档。

**去掉会怎样**：一个开脚本的用户能打满连接池，其他用户全部排队。

## 3. 熔断（Circuit Breaker）

**是什么**：下游连续失败时主动拒绝请求，防止雪崩。

**为什么需要**：DeepSeek 挂了，100 个请求各等 15 秒超时 = 100 个连接被占 15 秒 = 连接池耗尽 = 整个网关假死。

**本项目实现**：三态状态机（CLOSED/OPEN/HALF_OPEN），3 次失败熔断、30 秒半开试探、按端点隔离。

**去掉会怎样**：一次下游故障就能拖垮整个系统。

## 4. 语义缓存（Semantic Cache）

**是什么**：缓存"语义相同"的问题的答案，不重复调 LLM。

**为什么需要**：法律咨询场景重复率高，每次命中 = 省钱 + 省延迟。

**本项目实现**：三级金字塔（进程 LRU → sha256 精确 → pg_trgm 相似度 0.85），命中逐级回填。

**去掉会怎样**：每个重复问题都全价调一次 LLM，成本翻倍、响应变慢。

## 5. 冷热分层记忆（Memory Tiering）

**是什么**：把历史数据按访问频率分冷热两层存储。

**为什么需要**：LLM 无状态，需要历史上下文；热数据要快（Redis），冷数据要持久（PG）。

**本项目实现**：读 L1(Redis) → miss 回填；写 Redis 同步 + PG 异步（信号量限流 5 并发）。

**去掉会怎样**：要么每次对话都查 PG（慢），要么全放内存（重启即丢）。

## 6. 意图路由（Intent Routing）

**是什么**：判断"这个问题简单还是复杂、涉及哪些领域"。

**为什么需要**：简单问题走多 Agent = 浪费 10 倍 token 和延迟；复杂问题走单 Agent = 质量差。

**本项目实现**：关键词映射表（零成本）+ LLM 轻量分类（兜底）；决策出简单 / 复杂 / 全推荐三种路径。

**去掉会怎样**：所有问题都走最重的流程，成本和质量两头输。

## 7. 多 Agent 编排（Multi-Agent Orchestration）

**是什么**：让多个领域专家协作解决复杂问题。

**为什么需要**：单 Agent 对跨领域问题（"规划三天上海游"）会漏领域。

**本项目实现**：三阶段圆桌（并行工具 → 并行思考 → 交叉审阅 → 综合），asyncio.gather 并行。

**去掉会怎样**：复杂问题回答不全面，用户需要自己拼凑信息。

## 8. RAG（检索增强生成）

**是什么**：先从知识库检索相关资料，再让 LLM 基于资料回答。

**为什么需要**：LLM 训练数据有截止时间、会幻觉；知识库让回答"有据可依"。

**本项目实现**（民法典助手）：
- 知识库构建：民法典全文分块 + 向量化（768 维）
- 双通道召回：关键词（pg_trgm 模糊）+ 语义（向量相似度）
- 回答附法条出处
- 跨法域引导：法律映射表把"七天无理由退货"正确导向消保法

**去掉会怎样**：LLM 只能凭训练数据回答法律问题，容易幻觉、引用错误法条。

## 9. 分布式锁 + 乐观锁 + WAL

**是什么**：三个保证"钱算得对"的机制。

**为什么需要**：4 个实例可能同时操作同一个钱包，余额会算错。

**本项目实现**：
- 分布式锁（Redis SET NX EX）：防"同时进门"
- 乐观锁（version 字段 + WHERE version=$3）：防"出门时发现被改过"
- WAL 交易流水（只追加表）：流水 = 真相，可对账、不可篡改

**去掉会怎样**：并发充值/扣费会丢钱，账目无法审计。

## 10. 可观测性（Observability）

**是什么**：指标 + 链路 + 日志三件套，让系统内部"被看见"。

**为什么需要**：生产环境铁律——看不见 = 等于没有；问题没有证据只能靠猜。

**本项目实现**：
- Prometheus 指标：请求量、耗时、LLM token（钱）、缓存命中率、支付指标
- OpenTelemetry + Tempo：请求从入口到模型的每一步耗时瀑布图
- Loki + promtail：日志统一采集
- 业务观测：requests 表记录首 token 时间

**去掉会怎样**：用户说"好慢"，你只能猜是哪一环。

## 11. CI/CD

**是什么**：把"代码 → 构建 → 测试 → 部署"自动化。

**为什么需要**：手动部署慢、易错、有停机风险（4 实例同时重建 = 瞬间全挂）。

**本项目实现**：ci.sh 五阶段流水线 + 滚动部署（逐实例）+ 冒烟测试 + 自动回滚。

**去掉会怎样**：每次上线选半夜、全站停摆几分钟、出问题无法快速回退。

## 12. 数据库迁移（Alembic）

**是什么**：表结构变更的版本控制系统。

**为什么需要**：手动改表没有记录，线上库和代码永远对不上，改坏了无法回滚。

**本项目实现**：基线迁移固化 13 张表，今后变更都写迁移脚本，`upgrade`/`downgrade` 可回溯。

**去掉会怎样**：加一列靠手敲 SQL，上线后才发现生产库没执行。

## 13. SLO（服务目标）

**是什么**：用数字定义"服务健康"（错误率 <1%、p95 <5s）。

**为什么需要**："还行吧"无法管理，数字才能触发告警和扩容。

**本项目实现**：SLI/SLO 表 + 27 条告警规则 + 容量约束（单机 1GB 内存与实例上限）。

**去掉会怎样**：系统劣化到用户投诉才发现。

## 14. WAF（Web 防火墙）

**是什么**：在入口拦截恶意请求（SQL 注入、XSS、路径穿越）。

**为什么需要**：公网暴露的网关是攻击面，不能让恶意请求到达后端。

**本项目实现**：nginx map 特征匹配 → 命中直接 403，不打到后端；配合安全头、限流盾牌。

**去掉会怎样**：攻击请求直达后端，消耗资源、有数据泄露风险。

## 15. 密钥治理（Secret Management）

**是什么**：密钥（API Key、密码）从代码中剥离，统一从环境变量/配置文件读取。

**为什么需要**：硬编码密钥一旦进 git 历史就永久泄露；换 Key 要改代码重部署。

**本项目实现**：`_env.py` 统一读取 `.env`；清除 41 个文件硬编码；`.gitignore` 保护；轮换建议。

**去掉会怎样**：一次代码仓库泄露 = 所有密钥暴露 = 账户被刷爆。

## 16. 弹性伸缩 / 数据保留 / 备份

**是什么**：容量可调、数据有生命周期、灾难可恢复。

**为什么需要**：流量高峰加实例、数据无限增长会爆库、备份不能恢复等于没有备份。

**本项目实现**：scale 脚本（运行时加/减实例）、retention 脚本（按保留期清理）、restore_drill（恢复演练）。

**去掉会怎样**：高峰卡死、库被撑爆、出事故只能重来。
