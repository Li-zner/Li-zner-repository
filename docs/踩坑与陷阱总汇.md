## 一、环境与工具链（Windows / Docker / 终端）

1. **Docker 构建太慢**

   - 坑：`apt-get install tesseract-ocr` 国内网络极慢；`docker build --no-cache` 全量重建每次重装依赖（torch 20 分钟）。
   - 解法：利用层缓存（依赖层在代码 COPY 之前）；小改动用 `docker cp` + `docker restart`；不要 `--no-cache`。
2. **Docker 进程被 kill 后 CLI 不可用**

   - 坑：`taskkill /F /IM docker.exe` 干掉 CLI 进程 → `CommandNotFoundException`。
   - 解法：重启 Docker Desktop（`Start-Service com.docker.service`）。
3. **WSL bash 写 Windows 盘 pyc 权限失败**

   - 坑：`python -m compileall` 在 WSL 写 `app/__pycache__` 被拒。
   - 解法：语法检查用 `ast.parse` 纯解析，不写文件，任何环境兼容。
4. **wslrelay 拦截 localhost:5432**

   - 坑：Windows 宿主连 `localhost:5432` 被 `wslrelay.exe`（监听 127.0.0.1）拦截 → 认证失败；postgres 容器 IP 从宿主不可达（WSL2 桥接限制）。
   - 解法：可靠路径 = 局域网 IP（命中 `com.docker.backend` 的 0.0.0.0:5432）；`migrate.py` 自动探测（DB_HOST > localhost > 局域网 IP）。注：MCP 资产库实测 localhost 直连成功，需按环境验证。
5. **持久终端偶发损坏 + 推送输出被吞**

   - 坑：终端越长寿越频繁出现 `^U` 前缀、`git` 找不到、"Write-Output 无法识别"。
   - 根因（2026-08 确诊）：PowerShell 5.1 自带 PSReadLine 2.0.0 与 VS Code shell integration 的 OSC 序列冲突，注入 `\x15`(Ctrl-U) 吃掉命令开头。
   - 解法：升级 PSReadLine 2.4.5（新开终端生效）；出现 `^U` 就换新终端；`git push ... *> file; Get-Content file` 确认输出。
6. **Windows 中文路径 + venv ensurepip 失败**

   - 坑：`python -m venv` 在含中文路径（`D:\桌面\...`）下 ensurepip 报错。
   - 解法：避免在中文路径建 venv；或直接用已有解释器（本会话：系统 Python 已装 mcp/httpx，零安装直接跑）。
7. **pip 安装被沙箱/权限拒绝**

   - 坑：`pip install` 写系统 Temp 目录 `Permission denied`（受限环境）。
   - 解法：用完整权限执行安装；装包属一次性环境操作。

## 二、编码与字符集

8. **UTF-8 BOM 导致 json.load() 失败**

   - 坑：PowerShell `Set-Content -Encoding UTF8` 写入 BOM → `Unexpected UTF-8 BOM`。
   - 解法：读用 `utf-8-sig`；写用 `UTF8NoBOM`；容器内用 `utf-8-sig` 读后重写。
9. **PowerShell 管道传中文乱码（GBK）**

   - 坑：`@'...'@ | docker exec -i` 传中文按 GBK 编码 → 乱码/`???`。
   - 解法：中文代码写入 `.py` 文件 `docker cp` 进容器再执行；脚本控制台设 `PYTHONIOENCODING=utf-8`。
10. **控制台 GBK 显示乱码（外观问题）**

    - 坑：Python print emoji/中文在 Windows 控制台 `UnicodeEncodeError` 或乱码（代码页 936）。
    - 解法：`[Console]::OutputEncoding = UTF8` + `$env:PYTHONIOENCODING = "utf-8"`；程序里避免打印 emoji。
11. **alembic.ini 中文注释炸（GBK）**

    - 坑：Windows configparser 用 GBK 读 ini，UTF-8 中文注释 UnicodeDecodeError。
    - 解法：ini 文件保持 ASCII（纯英文注释）。
12. **CRLF 换行符**

    - 坑：bash 脚本 CRLF 在容器内炸。
    - 解法：脚本必须 LF；跨平台显式处理。
13. **env 文件尾部无换行 → 追加拼行（损坏配置）**

    - 坑：`echo "K=V" >> env` 拼到上一行，密钥互相污染。
    - 解法：追加前检查尾字节无 `\n` 先补空行；或 `printf '\n%s\n' "K=V" >> file`。

## 三、配置与密钥治理

14. **密钥硬编码 41 个文件**

    - 坑：DeepSeek Key、数据库密码、admin 密码散落代码 → 仓库泄露 = 全部泄露。
    - 解法：`_env.py` 统一读取；`config.py` 移除默认值（fail loudly）；`.gitignore`/`.dockerignore` 排除。
15. **configparser 遇密码 `%` 报错**

    - 坑：密码含 `%` 触发 invalid interpolation（`%23` 转义也炸）。
    - 解法：连接串绕过 ini，直接传引擎。
16. **双 env 文件分叉（配置漂移变体）**

    - 坑：安全目录（权威源）与根目录 .env 各缺各的键，改哪份都不生效。
    - 解法（2026-08 已对齐）：合并为一份完整版写入安全目录（root 优先+扩展键）；docker-compose 5 处 env_file 改指 UNC 路径；`_env.py` 增加 UNC 读取；根 .env 清空为占位注释。
    - **权限坑**：安全目录文件必须 644（compose/docker CLI/宿主脚本以普通用户经 UNC 读，600 全部 PermissionError）。
17. **配置漂移导致线上全链路故障（真实事故）**

    - 坑：容器内密码被外部改掉，git 配置仍是旧的 → 4 网关连库失败 → 登录 500 → 支付全链路挂。
    - 排查：`docker exec postgres env` 看真实环境变量 ≠ 配置文件。
    - 解法：密码统一收口 `.env`（gitignored）+ `env_file` 注入；改密码必须全链路探活；部署脚本加配置一致性校验。
18. **docker compose env_file 可直接读 UNC 路径**

    - 技巧：compose CLI 在 Windows 侧运行，`env_file` 支持 `\\wsl.localhost\Ubuntu\etc\...\\.env`（正反斜杠都行）——密钥可只存 WSL 安全目录，不落项目文件夹。
19. **env_file + `${VAR}` 取空值**

    - 坑：环境变量注入方式端到端没验证，容器内取到空。
    - 解法：注入方式端到端验证（`docker compose config` 看实际值）。

## 四、数据库与 PostgreSQL

20. **asyncpg 时区类型不兼容**

    - 坑：`datetime.now(timezone.utc)`（offset-aware）写不进 `TIMESTAMP`（naive）列。
    - 解法：用 `datetime.utcnow()`，或 isoformat 后加 `Z`。
21. **中文密码 URL 编码**

    - 坑：密码含 `#` `@` 在连接串/Shell 传参中炸。
    - 解法：`quote_plus` 编码；Shell 单引号包裹；不要手动拼 DATABASE_URL。
22. **慢查询拖垮连接池**

    - 坑：慢查询占住连接 → 池耗尽 → 全站变慢。
    - 解法：`pg_stat_statements` 监控 + 告警；`async with pool.acquire()` 保证归还。
23. **重复数据导入（md5 幂等失效场景）**

    - 坑：docx 与库内 content 微差（换行等）→ md5 不同 → 重复 chunk（1263 vs 1260）。
    - 解法：导入前按 chunk_key 去重；清理时"保留带 embedding 的，其次内容长的"。

## 五、Python 与异步

24. **协程里阻塞调用**

    - 坑：`time.sleep`、同步 requests 卡死事件循环。
    - 解法：IO 用 async；CPU 密集交线程/进程池；并发任务设信号量上限。
25. **异步落盘无保护**

    - 坑：`asyncio.create_task` 写库无信号量限流 → 高并发下连接池被写满。
    - 解法：信号量限流（如 5 并发）+ 异常兜底；生产级用 MQ（Redis Streams/RabbitMQ）替代进程内任务。
26. **逐条 INSERT + 远程探测太慢（超时）**

    - 坑：每条记录先探测 embedding 服务再插入，300 条卡死。
    - 解法：一次性探测服务可用性 + `executemany` 批量插入 + 每批打印进度。

## 六、AI / Agent 与检索

27. **模型级问题硬改 prompt 无效**

    - 坑：DeepSeek 顽固把"七天无理由退货"归到民法典，改 prompt 无效。
    - 解法：架构手段绕过——法律依据纠正映射表，命中直接返回引导（CC019 从 2 分到 7 分）。
28. **知识库构建正则漏导千位条号（重大缺陷）**

    - 坑：条号正则 `第[一二三四五六七八九十百]+条` 缺"千""零" → `第一千零四十条` 及之后全部无法匹配 → 第五~七编整编缺失（861 条只有四编）。
    - 解法：字符类加 `千万零`；docx 全量重解析（1260 条）幂等补缺（`mcp_assets/servers/civil-code-rag/import_civil_books.py`）。
29. **pg_trgm `%` 操作符对中文短查询失效 + 长句噪音**

    - 坑：`content % $1` 对 6 字查询相似度 0.0000（短查询×长文本 Jaccard 趋零）；对映射后的长句又返回含共同子词的噪音条款占满候选配额，挤掉 ILIKE 子词补充。
    - 解法：相似度全量排序（<0.1 丢弃）+ 子词 ILIKE 补充无条件执行（2-4 字滑动窗口拆词）。
30. **docx 是"目录 + 正文"双结构**

    - 坑：编标题出现两次（目录区+正文区），解析统计会被误导。
    - 解法：解析时以最后一次编标题为准（正文区），统计分布前先验证。
31. **语义缓存 L0 清不掉**

    - 坑：清 PG 表不清进程内 LRU（256 条）→ 仍命中旧缓存。
    - 解法：重启容器或等 LRU 自然淘汰。
32. **LLM 返回非法 JSON**

    - 坑：子 Agent 首轮返回非纯 JSON。
    - 解法：多级提取（直接解析 → markdown 块 → 花括号 → 修复未引用 key）+ 自动重试一次。

## 七、MCP 专项

33. **stdio 传输依赖命名管道，受限环境被拒（WinError 5）**

    - 坑：沙箱/受限环境禁止创建命名管道，`stdio_client` 拉起子进程即 `PermissionError`。
    - 解法：以完整权限运行 MCP 实验（这是协议特性，不是代码问题）。
34. **子进程 args 必须绝对路径**

    - 坑：相对路径 `weather_server.py` 按父进程 cwd 解析失败（`No such file`）。
    - 解法：`os.path.join(os.path.dirname(os.path.abspath(__file__)), server_script)`。
35. **Resource URI scheme 必须合法（RFC 3986）**

    - 坑：`civil_code://coverage` 的 scheme 含下划线 → pydantic AnyUrl 校验失败，Server 启动即崩。
    - 解法：scheme 只用字母数字 `+-.`（`civil://coverage`）。
36. **封装"能力"不是封装"流程"**

    - 坑：把"法律映射→口语映射→召回→Rerank→生成回答"打成一个黑盒 tool → Host 失去干预/成本/可观测。
    - 解法：Tool = 原子动作（检索）；领域知识（映射表）下沉 Server；生成回答留 Host；多 Agent 圆桌是编排逻辑，不封装成 tool。
37. **参数暴露是取舍不是越多越好**

    - 坑：参数越多 Host 越灵活，但模型越容易用错。
    - 解法：`top_k`/`use_rerank` 暴露、Rerank 阈值等内部策略默认值收在 Server（可覆盖）。
38. **依赖治理：自包含 vs 公共库**

    - 坑：MCP Server 直接 import 项目内部模块会拉起整个应用初始化（连接池/日志/配置）。
    - 解法：Server 代码自包含（只复用零依赖 `_env.py` 读配置 + 数据文件）；逻辑复制两份 → 后续再抽公共库。

## 八、部署与运维

39. **滚动发布 vs 全量重建**

    - 坑：4 实例同时 `--force-recreate` = 上线瞬间全站停摆。
    - 解法：一次只升级一个实例，健康检查过再动下一个；失败回滚（记录 PREV_IMAGE）。
40. **Docker DNS 不解析已停服务 → nginx reload 失败**

    - 坑：upstream 引用已停容器，`nginx -s reload` 报 `host not found` 失败，旧配置继续生效；轮询到死实例连接超时（login 499）。
    - 解法（2026-08 已对齐）：upstream 由 `autoscale.sh` 动态维护（幂等 reconcile）；所有 location 补 `proxy_connect_timeout 2s` + `proxy_next_upstream_tries 4`；不手工改 upstream。
41. **docker compose 与手动启动容器命名冲突**

    - 坑：`docker compose up -d` 报 container name already in use，`set -e` 直接中断。
    - 解法：基础设施步骤容错（已运行则继续，失败仅告警不阻断）。
42. **压测忘设 --run-time**

    - 坑：压测工具无限跑，工具使用也要有熔断意识。
    - 解法：压测命令显式限时。
43. **索引选型**

    - 坑：全表扫描退化（数据量上来后毫秒→秒级）。
    - 解法：B-tree（范围/等值）、GIN+trigram（模糊）、ivfflat（向量近似）；用 `EXPLAIN ANALYZE` 验证。

## 九、自检与测试（2026-08-16 补充，均来自 eval/验收工具自检实战）

44. **自检断言凭印象写数字，必挂**

    - 坑：给 `gate_failures` 写自检时凭感觉断言「整体 8.4 >= 8.0 各分类达标」，实际整体是 8.17、民法典分类只有 7.75——断言与真实计算不符，自检第一版必然失败。
    - 解法：断言数字先跑一遍真实输出再固化；或先打印中间值再写断言。
45. **纯函数参数顺序不清 → 断言写反**

    - 坑：`gate_failures(overall_avg, stats, threshold, ...)` 调用时把 overall 传成 8.5、threshold 传 8.0，断言「整体线失败」永不成立——参数错位让测试测了错误场景。
    - 解法：多参数调用用关键字传参；自检断言里写清「传入什么、期望什么」。
46. **测试没走业务同一路径（测试与实现分叉）**

    - 坑：语义缓存自检直接用 `L0.get()` 断言 TTL 过期行为，但业务路径是 `_l0_get()`（带过期淘汰）——测的是另一个函数，测了个寂寞。
    - 解法：抽公共函数，自检调用与业务完全相同的路径；测试与实现分叉 = 假绿。

## 十、MCP 客户端编程（2026-08-16 补充）

47. **stdio 会话清理期抛 ExceptionGroup 掩盖真实异常**

    - 坑：验收脚本里阶段断言失败后，`async with stdio_client(...)` 退出清理时 mcp SDK 的 TaskGroup 抛 `ExceptionGroup: unhandled errors in a TaskGroup`，把真正的 AssertionError 顶掉，报告只显示「执行异常」看不到根因。
    - 解法：阶段异常在上下文**内部**先捕获记录，退出后再上报；清理期异常仅在无阶段异常时才算失败（见 `AI应用验收工具/verify_all.py`）。
48. **工具里资源获取必须在 try 内（错误返回体化纪律）**

    - 坑：Redis Server 的 4 个工具把 `get_redis()` 放在 try 外——缺 redis 包/连接失败时抛异常，违反「错误返回 `{"error": ...}` 而非抛异常」；而单测里 `--self-check` 第一版也因顶层 import redis 直接崩。
    - 解法：连接获取与业务调用一起包 try；依赖包延迟 import（`--self-check` 无需外部包也能跑）。
