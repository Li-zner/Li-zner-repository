## 第 1 段：Redis 固定窗口限流（对应 `app/middleware/rate_limit.py`）

**面试题**：手写一个基于 Redis 的接口限流（QPS 限制）。

```python
import time

async def check_qps(r, username: str, limit: int) -> bool:
    """固定窗口限流：每秒一个 key，INCR 计数，超限拒绝"""
    key = f"qps:{username}:{int(time.time())}"
    count = await r.incr(key)
    if count == 1:
        await r.expire(key, 2)      # 首次创建时设过期，防止 key 堆积
    return count <= limit

async def check_concurrent(r, username: str, limit: int) -> bool:
    """并发计数：INCR 占位，超限 DECR 还回去"""
    key = f"concurrent:{username}"
    current = await r.incr(key)
    if current == 1:
        await r.expire(key, 30)     # 30 秒超时自动释放（防泄漏）
    if current > limit:
        await r.decr(key)           # 拒绝也要归还槽位
        return False
    return True
```

**手写要点**：① INCR 后首次设过期（防 key 无限堆积）② 并发计数超限要 DECR 归还 ③ 过期时间 = 兜底释放。
**面试追问**：固定窗口的缺陷？（窗口边界双倍流量）→ 滑动窗口/令牌桶怎么改？
**为什么面试考**：Redis 原子操作 + 资源释放意识，两个高频考点一次考到。

## 第 2 段：JWT 签发与校验（对应 `app/middleware/auth.py`）

**面试题**：手写 JWT 的创建和验证。

```python
import uuid
from datetime import datetime, timedelta
from jose import JWTError, jwt

SECRET_KEY = "..."          # 环境变量注入，禁止硬编码
ALGORITHM = "HS256"
ACCESS_EXPIRE_MINUTES = 120

def create_access_token(data: dict) -> str:
    to_encode = data.copy()
    now = datetime.utcnow()
    to_encode.update({
        "exp": now + timedelta(minutes=ACCESS_EXPIRE_MINUTES),
        "iat": now,
        "type": "access",
        "jti": uuid.uuid4().hex,      # 唯一 ID，用于吊销/黑名单
    })
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)

def decode_token(token: str) -> dict:
    try:
        return jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    except JWTError:
        raise ValueError("invalid token")
```

**手写要点**：① `exp` 必带（过期）② `jti` 用于吊销 ③ 解码必须捕获 JWTError。
**面试追问**：JWT 为什么无状态？（验签即验真，多实例天然适配）→ 泄露了怎么办？（短 access + refresh 轮换 + jti 黑名单）
**为什么面试考**：认证是每个后端系统的第一道题，JWT 是标准答案。

## 第 3 段：熔断器三态状态机（对应 `app/middleware/circuit_breaker.py`）

**面试题**：手写一个熔断器（CLOSED / OPEN / HALF_OPEN）。

```python
import time

class SimpleBreaker:
    def __init__(self, fail_threshold=3, recover_timeout=30):
        self.fail_threshold = fail_threshold
        self.recover_timeout = recover_timeout
        self.fail_count = 0
        self.state = "CLOSED"
        self.last_fail_time = 0

    async def call(self, async_func, *args, **kwargs):
        # OPEN：快速失败，不浪费连接
        if self.state == "OPEN":
            if time.time() - self.last_fail_time > self.recover_timeout:
                self.state = "HALF_OPEN"      # 恢复期到，放一个试探请求
            else:
                raise Exception("熔断器已开启")

        try:
            result = await async_func(*args, **kwargs)
            if self.state == "HALF_OPEN":
                self.state = "CLOSED"         # 试探成功 → 恢复
                self.fail_count = 0
            return result
        except Exception as e:
            self.fail_count += 1
            self.last_fail_time = time.time()
            if self.fail_count >= self.fail_threshold:
                self.state = "OPEN"           # 连续失败达阈值 → 熔断
                self.fail_count = 0
            raise e
```

**手写要点**：① 三态流转（OPEN 超时 → HALF_OPEN；试探成功 → CLOSED）② 失败计数在 CLOSED 时累计 ③ 按端点隔离（注册表）不全局一个。
**面试追问**：熔断和超时什么关系？（先超时，超时也算失败）→ 熔断后怎么降级？（返回兜底而非报错）
**为什么面试考**：纯状态机题，3 分钟能写完，考的是"防雪崩"意识。

## 第 4 段：LRU 缓存（对应 `app/core/semantic_cache.py` 的 L0）

**面试题**：手写 LRU（最近最少使用）缓存。

```python
import time
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int = 256, ttl: int = 600):
        self._cache = OrderedDict()       # key -> (value, expire_ts)
        self._capacity = capacity
        self._ttl = ttl

    def get(self, key):
        item = self._cache.get(key)
        if item is None:
            return None
        value, expire = item
        if time.time() > expire:
            self._cache.pop(key, None)    # 过期即淘汰
            return None
        self._cache.move_to_end(key)      # 移到尾部 = 最近使用
        return value

    def set(self, key, value):
        self._cache[key] = (value, time.time() + self._ttl)
        self._cache.move_to_end(key)
        if len(self._cache) > self._capacity:
            self._cache.popitem(last=False)   # 淘汰最久未用（头部）
```

**手写要点**：① `move_to_end` = 标记最近使用 ② `popitem(last=False)` = 淘汰最旧 ③ 容量检查在 set 时做。
**面试追问**：为什么 O(1)？（OrderedDict 双向链表 + 哈希）→ 不用 OrderedDict 怎么实现？（dict + 手写双向链表）
**为什么面试考**：数据结构经典题，考到概率极高。

## 第 5 段：分布式锁 + Lua 原子释放（对应 `app/payment/service.py`）

**面试题**：手写分布式锁，要求释放时校验持有者。

```python
import uuid

async def acquire_lock(r, key: str, ttl: int = 10):
    """SET NX EX：只有第一个能拿到；ttl 防持锁者崩溃后死锁"""
    token = uuid.uuid4().hex
    ok = await r.set(f"lock:{key}", token, nx=True, ex=ttl)
    return token if ok else None        # 拿不到返回 None

# Lua：仅值匹配才删除（原子：检查+删除一步完成，防误删他人锁）
_RELEASE_LUA = """
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
"""

async def release_lock(r, key: str, token: str):
    if not token:
        return
    await r.eval(_RELEASE_LUA, 1, f"lock:{key}", token)
```

**手写要点**：① `nx=True`（互斥）+ `ex=ttl`（防死锁）② 唯一 token（身份）③ 释放必须 Lua（不能先 get 再 delete，中间有窗口）。
**面试追问**：锁过期了操作没做完怎么办？（看门狗续期）→ 主从切换丢锁？（Redlock，但多数场景用不上）
**为什么面试考**：分布式锁三个坑（死锁/误删/过期）全考，你的代码是修复过真 bug 的版本。

## 第 6 段：乐观锁 UPDATE + 冲突重试（对应 `app/payment/service.py`）

**面试题**：用乐观锁更新余额，版本冲突时重试。

```python
async def do_update(conn, user_id: str, delta: int, version: int) -> bool:
    """CAS：版本对不上影响 0 行 = 冲突"""
    result = await conn.execute(
        "UPDATE user_wallets SET balance = balance + $1, version = version + 1 "
        "WHERE user_id = $2 AND version = $3",
        delta, user_id, version,
    )
    return "UPDATE 1" in result        # 必须检查结果！

async def apply_balance_change(conn, user_id: str, delta: int, max_retries: int = 3):
    """读版本 → 更新 → 冲突则重读重试（有上限，防无限空转）"""
    for _ in range(max_retries + 1):
        row = await conn.fetchrow(
            "SELECT balance, version FROM user_wallets WHERE user_id = $1", user_id)
        if not row:
            return False
        if await do_update(conn, user_id, delta, row["version"]):
            return True
        # 版本冲突 → 下一轮重读重试
    return False
```

**手写要点**：① `WHERE version = $3` 影响 0 行 = 冲突 ② **必须检查 UPDATE 结果**（不检查 = 余额没变流水照记）③ 重试必须有上限。
**面试追问**：乐观锁和悲观锁的选择？（读多写少用乐观，高冲突用悲观/队列）
**为什么面试考**：资金正确性 + 两个安全线（检查结果、有界重试），你踩过的 bug 就是答案。

## 第 7 段：asyncio.gather 并行 + 异常隔离（对应 `app/agents/orchestrator.py`）

**面试题**：多个协程并行执行，单个失败不影响整体。

```python
import asyncio

async def run_agents_parallel(agent_ids, call_fn):
    """多 Agent 并行：总耗时 = 最慢的一个，而不是相加"""
    tasks = []
    for agent_id in agent_ids:
        tasks.append(call_fn(agent_id))

    results = await asyncio.gather(*tasks, return_exceptions=True)  # 异常不抛出

    outputs = {}
    for idx, agent_id in enumerate(agent_ids):
        result = results[idx]
        if isinstance(result, Exception):
            result = {"error": str(result)[:50]}   # 失败降级，不拖垮整体
        outputs[agent_id] = result
    return outputs

# 并发上限控制（信号量）：防止一次性铺太多协程
_SEM = asyncio.Semaphore(10)

async def call_fn(agent_id):
    async with _SEM:
        await asyncio.sleep(1)      # 模拟 LLM 调用（IO 密集）
        return {"agent": agent_id}
```

**手写要点**：① `gather(..., return_exceptions=True)` 隔离异常 ② `isinstance(result, Exception)` 判断单个失败 ③ 并发任务要信号量设上限。
**面试追问**：协程里能放 `time.sleep` 吗？（不能，阻塞整个事件循环）→ 什么是 IO 密集？（await 时让出控制权）
**为什么面试考**：asyncio 是 AI 应用后端的核心（LLM 调用全是 IO 等待），并行 = 性能翻倍的关键。

## 第 8 段：FastAPI 依赖注入 + 认证（对应 `app/middleware/auth.py`）

**面试题**：用 FastAPI 依赖注入实现接口鉴权。

```python
from fastapi import Depends, FastAPI, HTTPException, Header
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

app = FastAPI()
security = HTTPBearer()

def verify_token(token: str) -> dict:
    # 实际项目里这里是 jwt.decode（见第 2 段）
    if token != "valid-token":
        raise HTTPException(401, "Invalid token")
    return {"username": "demo"}

async def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(security),
) -> dict:
    token = credentials.credentials
    try:
        payload = verify_token(token)
    except HTTPException:
        raise HTTPException(401, "Invalid token")
    return payload

@app.get("/api/profile")
async def profile(user: dict = Depends(get_current_user)):
    return {"user": user["username"]}    # 鉴权失败自动 401，业务代码零污染
```

**手写要点**：① `Depends` 注入依赖 ② 依赖里抛 HTTPException = 自动 401 ③ 业务函数只声明参数，鉴权逻辑完全复用。
**面试追问**：依赖注入的本质？（装饰器 + 函数参数解析）→ 怎么给特定接口加限流？（同样用 Depends 挂 rate_limit）
**为什么面试考**：FastAPI 的灵魂是依赖注入，面试官会问"你的鉴权怎么实现的"。
