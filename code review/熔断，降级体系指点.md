P0 级：协程并发安全灾难（直接导致计数器错乱）
1. 【P0-致命】SimpleBreaker 非线程/协程安全，多请求下状态错乱
文件：circuit_breaker.py (第 6~24 行)

代码：self.fail_count += 1、self.state = "OPEN" 无任何锁保护。

风险：FastAPI 是异步并发模型。当 10 个请求同时失败时，它们会同时读取 self.fail_count（比如都是 2），各自执行 +=1（写回 3），然后连续触发 10 次 state = "OPEN"。这会导致：

熔断器阈值彻底失效（本应连续失败 3 次才开启，结果 1 次并发失败就误开启）。

HALF_OPEN 状态在并发下被随意覆盖，导致熔断逻辑完全混乱。

修复：必须引入 asyncio.Lock 保护临界区，或者完全使用 Redis 原子操作（但鉴于您追求轻量，asyncio.Lock 对 200QPS 足够）。

🟡 P1 级：数据库与缓存架构硬伤

4. 【P1-并发泄漏】check_concurrent 的 expire 可能永不执行，导致资源耗尽
文件：rate_limit.py (第 51~57 行)

代码：if current == 1: await r.expire(key, 30)。

风险：假设用户 A 并发数为 1，执行 INCR 得到 1，正准备设置 EXPIRE，此时协程被挂起（或 CPU 时间片切换），另一个请求 B 进入，INCR 得到 2。虽然最终 B 也会执行 if current == 1（为假），不会设置过期时间。如果 A 在设置过期前异常退出，这个 Key 将永久存在，导致该用户并发槽位永远被占用，无法恢复。

修复（极简）：无条件执行 await r.expire(key, 30)。Redis 的 EXPIRE 开销极小，且幂等。既然 Key 已经存在，每次续期 30 秒是最安全的做法。

14. 【P1-分布式致命】QPS 限流依赖客户端时间（time.time()），服务器时钟漂移导致限流失效

15. 【P1-原子性缺失】update_daily_usage 的 TTL 设置条件导致 Key 永不过期
文件：rate_limit.py (第 86~89 行)

代码：if new_req == inc_request: await r.expire(req_key, ttl)

风险：这个判断假设“只有第一次 INCR 时才设置 TTL”。但如果 inc_request 传入 0（某些场景可能批量加 0），new_req == 0 为真，会设置 TTL。更严重的是：如果 Redis 因内存策略驱逐了该 Key，再次触发 INCR 时 new_req 等于 1，TTL 被重置。这没问题。

真正的漏洞：如果 inc_request 恰好等于当前值（极端情况），或者 Redis 返回了意外类型（如字符串），条件判断失效。标准做法是无条件设置 TTL（await r.expire(req_key, ttl)），EXPIRE 命令本身是幂等的，且开销极小。

27. 【P0-并发失控】check_concurrent 内部 DECR 与调用方 release_concurrent 重复释放槽位
文件：rate_limit.py (第 50~58 行) 与调用方（假设在中间件中）

风险链路：

请求 A 触发 check_concurrent，发现并发数已达上限（如 10）。
此时 check_concurrent 执行 await r.incr(key)（变为 11），检测 > limits["concurrent"]，执行 await r.decr(key)（退回 10），返回 False。
调用方（如中间件）收到 False 后，通常会在 finally 块中调用 release_concurrent。
致命错误：release_concurrent 再次执行 await r.decr(key)，将并发计数从 10 减为 9。
结果：系统实际仍有 10 个请求在处理，但 Redis 计数器显示只有 9 个。随后第 11 个请求通过检测，并发限制被穿透，且随着时间推移，计数器会持续低于真实值，限流完全失效。
修复铁律：check_concurrent 应只负责“放行并增加”，拒绝时不应修改计数器。拒绝由调用方直接抛异常，且禁止调用 release_concurrent。即：只有通过检查的请求才占用槽位，未通过的请求从始至终不占位。

    try:

    finally:
        await release_concurrent(user)  # 仅当 allowed=True 才释放

代码路径：

await r.set(f"auth:refresh_blacklist:{jti}", "1", ex=...) （拉黑旧 Token）
随后执行 user = await get_user(username) 和 create_access_token（签发新 Token）
风险：如果在第 1 步执行成功后、第 2 步执行前（例如数据库连接突然断开、应用收到 SIGTERM 被强制停止），旧 Token 已被撤销，但新 Token 未生成并返回给客户端。客户端持有的旧 Token 失效，且未获得新 Token，导致用户被强制踢下线且无法自助恢复（必须重新登录）。这在 Kubernetes 滚动更新期间极易触发。

修复铁律：先创建并返回新 Token，成功后再将旧 Token 加入黑名单（即“先建后删”），或使用 Redis 事务（MULTI/EXEC）保证原子性。

35. 【P1-异常遮蔽】release_concurrent 在 finally 块中未捕获异常，可能导致原始业务异常被覆盖
文件：rate_limit.py (第 60~65 行)

代码：async def release_concurrent(username): ... await r.decr(key)

风险场景：在 FastAPI 中间件或依赖项中，典型的调用模式是：

python
try:
    await check_concurrent(user)
    return await call_next(request)
finally:
    await release_concurrent(user)  # <-- 如果这里抛异常
如果 release_concurrent 中的 Redis 操作因网络超时而抛出异常，该异常会覆盖 call_next 中可能抛出的业务异常（如 400/500），导致客户端收到的错误信息完全错误（显示“并发释放失败”而非原始业务错误），且该异常会向上冒泡，可能绕过全局异常处理器。

修复：release_concurrent 内部必须使用 try...except 捕获所有异常并仅记录日志，绝不向外抛出异常（保证释放操作是“尽力而为”）。

🟡 P2 级：框架初始化与功能缺失
36. 【P2-隐式空指针】auth.py 中 oauth 对象未执行 init_app，GitHub 登录路由在运行时 500
文件：auth.py (第 117 行 oauth = OAuth()，第 121 行注册)

风险：authlib.integrations.starlette_client 需要调用 oauth.init_app(app) 将 OAuth 对象绑定到 Starlette/FastAPI 应用实例，以便挂载路由和中间件。当前代码仅注册了 github 客户端，但缺少 init_app 调用（或未将 app 对象传入 oauth 的构造上下文）。当用户访问 /auth/github/login 时，authlib 内部会因找不到 request.app 或 app.state 中的 OAuth 配置而抛出 AttributeError。

修复：在应用启动函数（如 lifespan 或 create_app）中显式调用 oauth.init_app(app)。

37. 【P2-访问令牌不可撤销】JWT 生成了 jti（JWT ID）但未持久化，导致无法主动踢人
文件：auth.py (第 55 行 "jti": uuid.uuid4().hex)

风险：您为访问令牌（Access Token）生成了唯一的 jti，但后端完全没有存储该 jti 及其过期时间。这意味着：

管理员无法在 Redis 中执行 DEL 操作来立即使某个访问令牌失效（即使实现黑名单，也需要存储所有有效 jti）。

如果用户被盗号或需要强制下线，只能等待自然过期（可能长达数小时），存在严重的安全响应滞后。

修复：在 create_access_token 中将 jti 写入 Redis（SETEX jti:{jti} 1 ACCESS_TOKEN_EXPIRE），并在 get_current_user 中校验该 jti 是否存在于 Redis（若不存在则拒绝）。但这会将无状态 JWT 变为有状态，权衡后可选，但既然您已生成 jti，当前实现属于“半成品状态”，建议要么彻底移除 jti（回归无状态），要么配套实现黑名单机制。

38. 【P2-断路器无超时控制】SimpleBreaker.call 未设置 asyncio.wait_for，下游慢请求会占满工作线程
文件：circuit_breaker.py (第 12~26 行)

风险：result = await async_func(*args, **kwargs) 直接 await，无超时包装。如果被保护的下游服务（如第三方 API）因网络问题挂起（如 TCP 半开），该协程会永久阻塞，导致 FastAPI 工作线程（或事件循环）被占用，最终耗尽所有可用连接。

修复：必须使用 asyncio.wait_for(async_func(*args, **kwargs), timeout=self.timeout) 并捕获 TimeoutError 计为失败。

🟢 P3 级：运维可观测性与边缘极端情况
39. 【P3-每日限额时区陷阱】date_str 来源于 datetime 但未显式指定时区，跨 UTC+8 零点时限额错乱
文件：rate_limit.py (第 76 行 get_daily_usage，第 86 行 update_daily_usage)

风险：调用方通常使用 datetime.utcnow().strftime("%Y%m%d") 生成 date_str。若服务器部署在 UTC+8 时区（如北京时间），业务日凌晨 00:00~08:00 期间，UTC 日期仍为“昨天”，导致用户每日限额在北京时间的凌晨被错误重置（提前重置），造成限额被盗用；或延迟重置，造成限额未恢复。

修复：强制统一使用 UTC 日期，并在注释中明确约定“所有日期配额按 UTC 日期对齐”（或从配置中注入 TIMEZONE）。

40. 【P3-断路器缺乏可观测性】状态变化（CLOSED -> OPEN）不记录任何日志或指标
文件：circuit_breaker.py (第 22~27 行)

风险：当熔断器触发开启或恢复关闭时，当前代码完全静默（无 logger.warning）。运维人员无法通过日志或 Grafana 监控得知下游服务是否故障，只能通过业务报错被动感知。在 200QPS 下，一个熔断事件可能在数秒内导致数百次失败，但日志中毫无踪迹。

修复：在状态变更时强制写入 logger.warning，并添加 Prometheus Counter 指标（breaker_state_changes_total）。
