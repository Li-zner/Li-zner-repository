FastAPI 生产级代码审查边界与要求文档
一、文档目的
本文档定义了 FastAPI 生产级项目的代码审查边界（审什么、不审什么）和要求（怎么审、按什么标准审），旨在将此前 67+ 项审查经验沉淀为可复用的审查规范，并结合 GitHub 开源社区的生产级最佳实践。

二、审查边界（Scope）
2.1 审查范围
层级	审查内容	优先级
P0 致命	数据丢失/损坏、服务不可用、资金安全、认证绕过、SQL注入	必须审
P1 高优	连接池泄露、超时未设置、事务边界错误、并发竞态、资源未释放	必须审
P2 中优	异常吞噬、日志缺失、配置硬编码、类型注解缺失	建议审
P3 低优	代码风格、命名规范、注释完整性	可选审
2.2 审查排除边界
以下内容不在本审查范围之内：

架构重写：如垂直拆分、目录重组（已确认暂不进行）

框架升级：如 FastAPI 版本升级、Python 版本升级

第三方库替换：如将 Redis 客户端替换为另一实现

UI/UX 相关：前端交互、API 响应格式美化

性能压测：实际压测执行（仅审查代码层面的性能隐患）

2.3 审查深度定义
深度级别	定义	适用场景
L1 表面审查	语法错误、明显 bug、导入缺失	快速 PR 检查
L2 逻辑审查	业务逻辑正确性、边界条件、异常分支	功能模块审查
L3 深度审查	并发安全、事务边界、连接池、缓存击穿、安全注入	本规范默认级别
L4 架构审查	模块耦合、可扩展性、技术选型	大版本重构时
三、审查要求（Standards）
3.1 输出格式要求
每条审查意见必须包含以下四个要素：

text
【问题编号】P0-001
【文件路径】app/payment/service.py
【行号锚点】第 180-195 行
【问题描述】事务内调用外部渠道（channel.pay），数据库连接在整个休眠期间被独占，连接池耗尽时服务死锁
【风险等级】P0
【修复方案】[具体代码 diff 或完整函数替换]
【参考依据】GitHub fastapi-best-practices #async-routes[reference:2]
3.2 风险等级定义
等级	定义	响应时间
P0	会导致数据丢失/损坏、服务宕机、资金损失、安全漏洞	立即修复（24h内）
P1	高并发下会触发、长期运行会导致资源泄漏、影响用户体验	本周内修复
P2	影响可维护性、可观测性、边缘场景下可能出问题	本月内修复
P3	代码风格、注释、命名等优化项	可延后或忽略
3.3 审查维度 Checklist
3.3.1 异步正确性（Async Correctness）
□ 所有 I/O 操作是否使用了 await？（缺失 await 会导致协程不执行）
□ 同步阻塞代码（如 time.sleep()、requests.get()）是否在异步函数中出现？（会阻塞事件循环）
□ asyncio.create_task() 创建的后台任务是否有异常处理？
□ 并发操作共享可变状态时是否有锁保护？（asyncio 单线程下仍有逻辑竞态）
□ 是否使用了 asyncio.gather() 但未处理部分任务失败的情况？
3.3.2 数据库与连接池
□ 连接池大小是否合理配置？（pool_size、max_overflow、pool_pre_ping）
□ 连接获取是否有超时设置？（pool.acquire(timeout=...)）
□ 事务边界是否清晰？（事务内是否包含外部 I/O 调用？）
□ 是否每个写操作都在显式事务中？（async with conn.transaction()）
□ 连接是否在请求结束后正确释放？（使用 yield 依赖或 finally 块）
□ 连接池是否在应用启动时初始化、关闭时清理？（使用 lifespan）
3.3.3 Redis 与缓存
□ Redis 操作是否设置了超时？（timeout 参数）
□ 缓存读取是否有击穿防护？（缓存失效时大量请求同时穿透到 DB【已发现 #1/#32】）
□ 缓存写入是否处理了异常？（写入失败不应影响主流程）
□ 分布式锁的获取和释放是否原子？（使用 Lua 脚本）
□ 锁的 TTL 是否大于业务预估耗时？（是否有看门狗续期机制）
□ Key 的命名是否有命名空间冲突风险？
3.3.4 安全
□ 认证与授权：JWT 是否校验了 type 字段？（防止 refresh token 当 access 用）
□ 输入验证：所有用户输入是否经过 Pydantic 校验？
□ SQL 注入：动态 SQL 是否使用参数化查询？
□ 敏感信息：日志中是否包含密码、API Key、Token？
□ CORS：生产环境是否限制 allow_origins？
□ 文件上传：是否校验文件类型、大小，是否有 Zip Slip 防护？
□ 请求体大小：是否配置了 max_body_size 限制？
3.3.5 异常处理与可观测性
□ 是否有全局异常处理器？（而非在每个 endpoint 中 try/except）
□ 关键路径是否有结构化日志？（包含 trace_id、user_id、order_no）
□ 是否有健康检查端点？（/health、/ready，用于 K8s 探测）
□ 是否有 Prometheus 指标？（请求数、错误数、延迟、业务指标）
□ 异常是否被静默吞噬？（except Exception: pass 是反模式）
3.3.6 配置管理
□ 配置是否使用 Pydantic BaseSettings 管理？
□ 敏感配置（SECRET_KEY、API_KEY）是否从环境变量读取？
□ 是否有配置默认值？默认值是否合理？
□ 配置变更是否需要重启？（是否支持热加载？）
3.3.7 资源管理
□ 文件句柄是否正确关闭？（使用 with 上下文管理器）
□ 数据库连接是否正确释放？（使用 async with 或 yield 依赖）
□ 后台任务是否在应用关闭时正确清理？
□ 是否存在内存泄漏风险？（全局列表/字典无限增长）
3.3.8 并发与竞态
□ 全局可变状态是否有锁保护？（asyncio 下推荐 asyncio.Lock）
□ Redis 操作是否原子？（使用 Lua 脚本或 WATCH/MULTI/EXEC）
□ 乐观锁的版本冲突是否有重试机制？重试是否有退避？
□ 分布式锁的获取顺序是否可能导致死锁？（先拿连接还是先拿锁？【已发现 #41】）
3.3.9 测试与 CI
□ 是否有单元测试和集成测试？（覆盖率建议 > 80%）
□ 是否配置了静态检查？（ruff、mypy、pylint）
□ PR 流程是否自动触发审查？（GitHub Actions）
四、常见问题分类（基于 67+ 项审查经验）
4.1 致命类（P0）—— 必须 0 容忍
问题模式	典型表现	参考案例
缓存击穿	缓存失效时大量请求同时打到 DB/LLM	#1, #32
事务内 I/O	事务中调用外部 API，连接被长期占用	#33
锁顺序死锁	先拿 Redis 锁再拿数据库连接	#41

启动崩溃	模块导入时读取不存在的文件	#59
上下文溢出	messages 列表无限累积	#60
4.2 高风险类（P1）—— 高并发下必现
问题模式	典型表现	参考案例
无超时	连接获取、Redis 操作、HTTP 调用均无超时	#18, #19
资源泄漏	文件句柄、数据库连接未释放	#6
竞态条件	全局缓存无锁初始化	#8

5.1 关键最佳实践摘录
项目结构：采用 routers/、services/、repositories/、models/ 分层

异步路由：I/O 密集型路由使用 async def，CPU 密集型使用 def + run_in_executor

Pydantic 优先：所有输入输出使用 Pydantic 模型验证

依赖注入：使用 Annotated[Type, Depends(...)] 模式（Pydantic v2 最佳实践）

配置管理：使用 Pydantic BaseSettings 管理所有配置

连接池：配置 pool_pre_ping=True 防止断连，pool_recycle 防止长连接超时

测试：从第一天起使用异步测试客户端
