# 审阅 Prompt（编码完成后使用）

> **用途**：对已实现的代码做逐文件审阅，输出 P0/P1/P2 分级问题清单 + 修复建议。
> **何时用**：编码完成（或完成一个模块）后，人类逐步对全部代码审阅时。
> **产出**：审阅报告（用 `../03-支撑资产/审阅报告模板.md`），P0/P1 修复后复验，P2 记录留待处理。

---

## 使用前准备（人类做）

1. 拿到需求库验收标准：`01-需求库/<项目>-需求.md` 与 `../01-需求库/模板-02-验收标准与MVP.md`
2. 确定审阅范围：单文件 / 单模块 / 全量
3. 把「验收标准与 MVP」填到下方【验收对照】区（或注明引用路径）

## 可复制 Prompt

```
你是一名严格的代码审阅专家。审阅以下代码，逐文件给出分级问题清单。

【审阅范围】
- 文件/模块：<文件或模块路径列表，或「全量」>
- 对应需求：<需求文件路径>
- 底层纪律：先读 `../00-底层规则/底层规则.md` 并遵守（通用纪律唯一权威源）

【第一步：先对照验收标准】
以下为本项目验收标准与 MVP 范围（编码前定稿，审阅以此为准）：
<在此粘贴验收标准与MVP，或注明：见 01-需求库/<项目>-需求.md 验收区>

【第二步：逐文件审阅，按 5 层审查模型（L1-L5）】
对每个文件严格按五层执行（来源：vbcoding 4 层审查模型；L5 借鉴 qodo-ai/pr-agent「tests」维度）：

L1 执行流（跑得起来吗）：
- 未处理的 await？缺失的依赖导入？类型注解错误？

L2 业务逻辑（对不对）：
- 所有数据库【写操作】是否有事务保护（如 `async with conn.transaction()`）？
- 是否存在「先插入再查询」的竞态窗口？若有 → 推荐改写为 RETURNING 合并 SQL
- 事务 / 幂等 / 并发锁是否按 `../03-支撑资产/ARCHITECTURE_RULES.md` 落实？（乐观锁 Version / 分布式锁 / 幂等键）

L3 防御与安全（安不安全）：
- 请求体大小是否限制？（Pydantic max_length / request.json() 带 limit）
- 是否向前端输出敏感堆栈 / error 字段含内部信息？
- OAuth 回调是否存在 CSRF 或账号劫持风险？
- 无硬编码密钥？SQL 参数化？敏感数据脱敏？限流/鉴权就位？

L4 生态对标（能不能更精）：
- 对比 Github 同类实现，哪些代码可用成熟开源库替代、压减代码量 50% 以上？
- 直接给出具体修改代码块，不留旧注释（成熟库优先见 `../03-支撑资产/ARCHITECTURE_RULES.md`）

L5 测试完备（够不够测，借鉴 pr-agent「tests」维度）：
- 核心路径有测试吗？边界 / 异常分支覆盖了吗？
- 修 Bug 的改动有没有把复现用例固化为回归测试？
- 测试是真断言还是摆设（无 assert / 永真断言 / 只跑不判）？

【第三步：输出分级问题清单】
按严重程度分级（对应 5 层模型）：
- P0（必须修）：安全漏洞（L3）/ 数据错误与并发竞态（L2）/ 核心功能不工作（L1）/ 违反红线
- P1（应当修）：边界漏洞 / 错误处理缺失（L3）/ 测试缺失（L5）/ 明显效率问题 / 结构违规（L1）
- P2（建议修）：生态对标可精简项（L4，用成熟库替代压代码量）/ 可读性 / 风格 / 待专项

每个文件标注审阅成本（低/中/高，借鉴 pr-agent「review effort」）；成本高者给出拆分建议，列入 P2。

【第四步：输出验收对照表】
逐条核验验收标准：通过 / 未通过（原因）/ 无法验证（缺什么）

【输出格式】
用 `../03-支撑资产/审阅报告模板.md` 的结构，诚实报告，不报喜不报忧。
```

---

## 使用要点（人类）

- **逐文件审阅**：一次审一个文件/模块，聚焦，别贪多（参考：可复用资产的 7 轮 review 即逐文件夹进行）
- **结对审查**：你作为 Vibe Coder 不肉眼逐行看——新建窗口把「审阅-prompt 可复制段」喂给 AI 审，你只看分级结果并决策
- **P0/P1 必须修**：修完重跑该文件相关测试，再复验
- **P2 记录**：登记进报告「P2 待处理」区（L4 生态对标项多归此），专项时处理，不许假装清零
- **验收对照不通过项**：回到编码阶段修，或回需求库改验收（需人确认，AI 无权改需求）
- **收敛闭环**：P0/P1 修复后走「对照验收标准 → 复测 → 收敛」才算闭环，不许修完即宣称完成
  （见 `../03-支撑资产/收敛循环.md` 第 4 节）
- **回写需求库**：审阅若暴露需求/协议/验收标准本身要改 → 人确认后回写 `01-需求库/` 定稿文件，
  并在审阅报告「需求库回写记录」登记（文档随代码一起活，借鉴 OpenSpec living documentation）
- **复用**：审阅时参考 `../../harness/03-参考-项目经验/03-踩坑清单.md` 对照已知坑；本 prompt 与「AI Agent 开发全流程」技能阶段 6 相互印证
