# 工作规则（AI 硬约束 + 流程交付）

> 无论接到什么任务，以下规则是底线。违反任何一条即视为任务失败。

## 1. 动手前

1. 先读 `00-主人意图与使用方法.md`（**必读第一份**）→ `00-README.md` → `04-待人类填写/` 全部。
2. `04-待人类填写/` 是**人类决策区**：只读，不许改；遇到 `[待定]` 停下询问，禁止猜测。
3. 发现以下任一情况，必须停下询问人类：端口/协议/错误码未定义或冲突；业务规则表述不清；
   凭据缺失或指向不明；验收标准无法推导。

## 2. 编码

4. 每段代码/每个函数必须带注释（做什么、为什么）；禁止 emoji（用户要求除外）；统一 LF 换行。
5. 业务逻辑禁止写进路由层；路由只做校验 + 调 service + 组装响应。
6. 数据库结构变更必须走迁移（Alembic），禁止手工 ALTER。
7. 密钥一律走安全目录（见 `01-编码与安全规范.md`），禁止硬编码。

## 3. 执行过程

8. 复杂任务必须先列 TODO，逐项完成、逐项勾选；每步先自测再进入下一步。
9. 复用 `02-模板/` 与 `03-参考-项目经验/` 已验证的模式，不重复造轮子。
10. 改动前先读目标文件当前内容（防止覆盖他人改动）；涉及多文件的改动先列 TODO。

## 4. 交付

11. **每次工作结束必须执行写后检查**（见 `02-防熵机制.md`）：函数 ≤80 行 / 文件 ≤600 行
    当场重构不隔夜，逻辑质量自查，结论写入交付报告。
12. 每次交付按 `05-执行流程/04-交付报告模板.md` 输出：完成项 / 差异项 / 风险项 /
    待人工确认项 / 自测证据。报告必须诚实，不报喜不报忧。
13. 未经验收清单（`05-执行流程/03-验收清单.md`）不得宣称「完成」。

## 5. Git 与工程卫生

14. 分支：`main` 稳定主干，功能用分支；提交信息 `type(scope): 描述`。
15. 提交前确认：无密钥、无调试残留、无无关文件；`.gitignore` 覆盖 `.env`/备份/临时文件。
16. `.sh`/`nginx.conf` 等脚本维护文件强制 LF（`.gitattributes` 写入 `eol=lf`）；
    语法检查用 `ast.parse`（不写 .pyc，兼容 WSL/Windows）。
17. 发现新的坑 → 追加到 `03-参考-项目经验/03-踩坑清单.md`。
