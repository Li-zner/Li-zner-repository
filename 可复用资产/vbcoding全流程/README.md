# vbcoding 全流程

> 一套「以需求驱动、协议先行、资产复用、审阅兜底」的 AI 辅助开发完整流程。
> 定位：给每个新项目的 AI 开发提供**固定顺序、固定模板、固定约束**，减少 vibe coding 的随意性。

## 核心理念

Vibe coding 不是「让 AI 随便写」，而是**人定方向、AI 出实现、流程兜质量**。本流程把这一过程固化成七个阶段：

```
拆解需求 → 建立架构（图谱/背景） → 协议先行 → 投喂可复用资产
→ AI 写骨架 → 按需求逐个实现功能 → 审阅代码 → 提交测试
```

每个阶段都有一份对应文件，照着走即可，通用任何项目（Python/FastAPI、Node、Web、Agent 均适用）。

## agent 按需读取模型（重要）

本目录为 agent 设计了**三层按需读取**，不要把全部文件一次性投喂：

| 层 | 何时读 | 内容 | 约合 token |
|---|---|---|---|
| L0 必读 | 每次会话开始，读一次全程有效 | `AGENTS.md`（路由）+ `00-底层规则/底层规则.md`（通用纪律唯一权威源） | 约 2k |
| L1 任务入口 | 按当前任务类型，**只读一个** | `02-任务-prompt/`：编码 / 修复bug / 审阅 | 约 0.5k~1k |
| L2 支撑资产 | L1 入口指明「何时读哪个」，不提前读 | `03-支撑资产/`：架构规则 / 编码规则 / 边界约束 / 收敛循环 / 审阅报告模板 | 每个 0.3k~0.7k |

- 任务中途切换类型（如编码改修 Bug）→ 回 `AGENTS.md` 路由表换读对应入口
- 某条规则不懂细节 → 按 `AGENTS.md`「细节下钻」索引读原文（原文在 `../harness/01-规则/`，
  该目录有自己的 README 索引，标注每份原文「内容 + 什么时候读」；不要预防性全读）
- 一次编码任务完整加载约 0.8万~1万 token；修 Bug 约一半

## 三个靶向 Prompt 模块（审查前置，来自 vbcoding.txt）

把审查思维**拆成三段、嵌入编码前**，让 AI 从第一行代码就规避问题，而不是写完了再改：

| 模块 | 嵌入阶段 | 文件 | 核心约束 |
|---|---|---|---|
| 架构规则 | 架构与协议（写骨架前） | `03-支撑资产/ARCHITECTURE_RULES.md` | 事务边界 / 并发竞争点声明 / 成熟库优先 |
| 强制自检清单 | 每个功能实现前 | `03-支撑资产/边界约束.md` 第 7 节 | Pydantic 输入防御 / 无状态 JWT / 密码禁截断 / 外部失败 503 |
| 5 层审查模型 | 编码完成审阅 | `02-任务-prompt/审阅-prompt.md` | L1 执行流 / L2 业务逻辑 / L3 防御安全 / L4 生态对标 / L5 测试完备 |

## 核心理念（为什么要审查前置）

- Vibe Coder 的核心竞争力是**给 AI 下指令的质量**，不是亲手敲代码
- 约束写进 System Prompt / 规则文件，让规则成为 AI 的**肌肉记忆**，而不是每次靠人提醒
- AI 一次做不对是常态：靠「收敛循环」（实现 → 对照 → 补任务 → 再实现）让缺口显式化，循环到验收全过，不假装一次通过
- **不要把所有优化点写成 MCP 工具**（太重）；把强制约束写进 prompt 规则文件即可
- 审查前置做扎实，你后续只需关注**需求拆解**和**协议设计**，不用天天给 AI 擦屁股改 Bug

## 使用顺序（每个新项目）

1. **启动**：在 `01-需求库/` 下新建一个以项目命名的文件，复制 `模板-01`、`模板-02` 填写
2. **填需求**：把项目背景、需求拆解、架构图谱（文字版）、协议、验收标准、MVP 全部写清；
   定稿前过一遍 `模板-01` 第 6 节澄清环节，全部澄清后才算定稿
3. **编码**：让 agent 读 `AGENTS.md` 路由到 `02-任务-prompt/编码-prompt.md`，把「需求文件」
   与「资产清单」填进去交给 AI；AI 先做跨文档一致性检查，再按收敛循环实现（不收敛不进审阅）
4. **审阅**：AI 实现完一个（或全部）功能后，走 `02-任务-prompt/审阅-prompt.md`，逐份代码审阅；
   审阅导致的定稿变更，人确认后回写需求库并在审阅报告登记
5. **测试提交**：按需求库验收标准 + 编码规则硬门禁跑测试，通过后提交

## 变更分级（流程按体量缩放）

> 借鉴 BMAD-METHOD 的 right-sized process：不是每次改动都要走全套七阶段，动手前先分级。
> **S/M/L 判定标准、流程与自判规则的唯一权威源在 `AGENTS.md`「变更分级」**，本节不重复，避免两处漂移。
> 摘要：S 微改动直改自测；M 单功能走对应任务入口 + 收敛小循环；L 新项目/大特性走全套七阶段；
> 凡要动协议、数据表结构、鉴权一律按 L。分级先由 agent 自判并报告「级别 + 理由 + 建议」，人类确认后执行。

## 通用性保证

- 所有模板**不含任何具体业务**，只含「填什么、怎么填、为什么」
- 编码规则/边界约束与具体技术栈解耦（Python/JS/Agent 通用），特殊项（如 Alembic）标注「按项目选用」
- 每个文件开头有「用途 / 何时用 / 填写人」，独立可用
