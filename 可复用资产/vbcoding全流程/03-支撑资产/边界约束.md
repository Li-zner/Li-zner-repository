# 边界约束（禁止清单 / 信任边界）

> **用途**：明确「AI 绝对不能做什么」——比「该做什么」更重要。编码-prompt 会引用本文件；审阅阶段逐条核验。
> **何时用**：编码全程 + 审阅对照。
> **通用性**：以下约束与语言/技术栈无关；项目特殊约束追加到项目需求库文件末尾。

---

## 1. 需求边界

- [ ] **不做需求外的事**：只实现需求库列出的功能；「顺手优化」「顺手重构」必须先登记、人确认，否则拒绝
- [ ] **不擅自扩范围**：遇到需求未覆盖但「好像需要」的场景 → 提出，不擅自实现
- [ ] **不删改需求库**：需求文件是定稿，AI 无权改动；有矛盾 → 停下问人

## 2. 代码边界

- [ ] **不改动未要求改的文件**：除非修复该功能必需，否则不动无关代码（防止副作用）
- [ ] **不重写他人可工作代码**：已有代码能跑就改，不推倒重来（「我写得更好」不是理由）
- [ ] **不留死代码**：删掉的逻辑不留注释掉的尸体；临时调试代码提交前清除
- [ ] **不制造超限函数/文件**：函数 ≤80 行 / 文件 ≤600 行，违规当场拆

## 3. 密钥与敏感数据边界（红线）

- [ ] **密钥绝不硬编码**：不写进代码、配置、README；统一走安全目录 `.env`
- [ ] **`.env` 绝不进 git**：提交前确认，含历史也要清理
- [ ] **日志/响应绝不含敏感明文**：密码、Token、API Key、手机号、身份证号一律脱敏
- [ ] **数据库错误不直接透出**：DSN/密码/内部路径脱敏
- [ ] **不给密钥兜底默认值**：缺失必须启动失败（fail loudly）

## 4. 信任边界

- [ ] **用户输入/上传/回调都是不可信**：进上下文前清洗（防提示词注入）、上传做扩展名+MIME+内容特征检测
- [ ] **SQL 全部参数化**：禁止字符串拼接
- [ ] **不盲信第三方返回**：外部 API 返回值先校验再使用
- [ ] **权限不过度开放**：接口按最小权限设计；管理接口有鉴权校验

## 5. 数据边界

- [ ] **不碰生产数据做实验**：验证用测试数据 / `__test__` 前缀，不写脏真实业务数据
- [ ] **不导出业务数据**：用户数据导出需明确授权
- [ ] **不丢数据**：破坏性操作（DELETE/清表/覆盖）先确认；迁移有回滚路径

## 6. 流程边界

- [ ] **每步自测再进下一步**：本切片测试没过，不进入下一个功能
- [ ] **不跳过硬门禁**：`check_code_rules.py` 等门禁必须过，禁止 `|| true` 跳过
- [ ] **不假装完成**：SKIP 要说明原因；没做的如实说「没做」
- [ ] **遇到 [待定]/矛盾/凭据缺失 → 停下问人**，禁止猜测

## 7. 强制自检清单（写每个功能前必过，vbcoding 硬约束）

> 来源：vbcoding.txt「生成骨架与功能实现阶段」硬约束。把本清单贴在每次写功能前的 Prompt 里。

- [ ] **输入防御**：所有接收 JSON 的接口必须用 Pydantic BaseModel 定义字段，且必须 `Field(..., max_length=XXX)`；若用手写 `await request.json()`，必须携带 `limit=1_000_000`（防超大体）
- [ ] **无状态原则**：认证一律 JWT Bearer，禁止 SessionMiddleware 或本地内存做认证状态
      （例外：OAuth 登录 state 可短暂用 Session，见项目已决策；除此之外不引入）
- [ ] **密码安全**：禁止静默截断 bcrypt 密码；超过 72 字节必须显式处理——二选一：
      简单方案：直接返回 400（vbcoding.txt 原案）；推荐方案：SHA-256 预处理全链路（哈希结果加 `$bcrypt-sha256$` 前缀标记）
- [ ] **幂等与失败**：依赖外部服务（短信/邮件/发 Token）的操作，失败时必须抛 5xx（如 `HTTPException(503)`），严禁返回「成功」状态欺骗前端
- [ ] **并发写入**：扣减/累加/抢锁类操作，必须有事务 + 锁/乐观锁保护（见 `ARCHITECTURE_RULES.md`）
