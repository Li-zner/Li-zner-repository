# 生产级系统设计参考（agent_gateway 验证过的四套范式）

> ⚠️ 参考，不是规则。每套给「适用场景 + 设计要点 + 关键注意」。
> 与 `02-机制库参考.md`（15 项机制）配套：机制是零件，这里是整机设计。

---

## 一、高并发 AI 网关（入口范式）

**适用**：任何"用户 → AI 服务"的中间层；需要认证/限流/计量/观测统一落点。

**设计要点（七层）**：
1. **入口**：Nginx 轮询 + 被动健康检查（max_fails + fail_timeout），服务无状态才能轮询
2. **无状态**：JWT 验签即真（不存会话）→ 任意实例可处理任意请求 → 横向扩展的前提
3. **认证**：access 短时效（2h）+ refresh 轮换 + jti 黑名单（Redis）
4. **限流**：Redis 四维（QPS/并发/日请求/日 token）+ 角色分级；并发计数超限必须 DECR 归还
5. **熔断**：三态状态机（CLOSED→OPEN→HALF_OPEN）+ 按端点隔离注册表
6. **缓存**：语义缓存三级（内存 LRU→精确哈希→相似度）+ 缓存三兄弟对策（见二）
7. **降级**：模型失败→次级模型→兜底链；工具超时→空结果继续（不整体失败）

**容量计算**：单实例并发 × 实例数 = 基线（4×200=800）；AI 网关瓶颈不在 CPU 在**连接池与下游限流**（asyncio 挂起等待是 IO 密集）。

**注意**：缓存与记忆写在门（中间层）上，业务在门后；门不写业务逻辑。

## 二、缓存一致性（缓存三兄弟 + 一致性选型）

**适用**：一切"读多写少"、可接受短暂不一致的场景（AI 答案缓存天然如此）。

**三个必防问题**：
- **穿透**（查不存在）：短 TTL 空值占位（`__EMPTY__` + 30s）——防重复打底层
- **击穿**（热点失效瞬间）：互斥重建锁（Redis SET NX + Lua 条件释放）——只允许一个重建，其他等待重读
- **雪崩**（集体失效）：随机 TTL（300-900s 抖动）——错开失效时刻

**一致性选型**（按数据特性）：
| 场景 | 方案 |
|---|---|
| 答案/配置类缓存（基本不变） | TTL 弱一致即可（默认选择） |
| 写频繁、需即时生效 | 失效通知（更新时主动清各级缓存） |
| 强一致 | 版本号对比或不用缓存 |

**注意**：L0 是进程内存，清库操作"看不到"它——清库后需重启（或接受自然过期）。多实例时 L0 各自独立，命中率与实例数相关。

## 三、消息队列（异步可靠性升级）

**适用**：需要"跨进程、可持久、可重试"的异步（异步落库、通知、任务分发）。进程内 `asyncio.create_task` 的边界：重启即丢、多实例重复、无重试。

**选型表**：
| 需求 | 选型 |
|---|---|
| 轻量异步、已有 Redis | **Redis Streams**（XADD/XREADGROUP/XACK；PEL 天然支持失败重试） |
| 通用业务消息、路由/ACK 语义 | RabbitMQ |
| 高吞吐事件流、日志/审计 | Kafka |

**落地要点（Redis Streams 模式）**：
```
生产者：XADD memory:write（消息入队即返回）
消费者（独立进程）：XREADGROUP 阻塞读 → 写 PG → XACK 确认
失败：消息留在 PEL（Pending Entries List）→ 可重试/死信
```
**注意**：选型匹配场景——不是最重的最好，是最合适的最好（万级/秒以内选 Streams 不选 Kafka）。

## 四、分布式事务与数据安全（资金一致性范式）

**这是数据库/资金一致性的生产级安全范式**——业界主流"业务级最终一致"，组件全部标准件：

```
本地事务（原子） + 分布式锁（防重入） + 乐观锁（防冲突）
+ WAL 流水（可对账） + 幂等（防重复） + 对账（兜底）
```

| 组件 | 解决什么 | 关键注意 |
|---|---|---|
| **本地事务**（单库 `transaction()`） | 多表操作原子性（余额+流水同生共死） | 事务要短；资金操作先取锁再开事务 |
| **分布式锁** | 并发防重入（同时进门） | `SET NX EX` + 唯一 token；释放必须 Lua 校验持有者；长任务看门狗续期 |
| **乐观锁** | 数据版本冲突（出门校验） | `WHERE version=$n` 影响 0 行=冲突；**必须检查 UPDATE 结果**；重试有上限 |
| **WAL 流水**（只追加表） | 真相可审计、不可篡改 | 流水=事实；余额可重算，流水不可删 |
| **幂等**（订单状态机） | 重复请求/回调不重复扣 | 状态机（pending→success 只走一次）+ 唯一索引双保险 |
| **对账**（每日 reconcile） | 系统性遗漏兜底 | 订单 vs 流水 vs 渠道三方比对；不一致告警 |

**方案强度认知**：2PC（阻塞/单点，基本弃用）→ TCC（实现重）→ Saga（补偿）→ **本地事务+幂等+对账（90% 场景够用）**。支付宝式方案本质也是"本地事务+异步回调+对账"。
**本质**：这是**简化版 Saga**——每个本地事务 + 状态机补偿（订单状态承担 Cancel 职责），最终一致。

**悲观锁（SELECT FOR UPDATE）的定位**：
- 本范式默认不用悲观锁：冲突率低时（用户各管各钱包），乐观锁重试（≤3 次）足够，悲观锁的阻塞代价白付
- **必须用悲观的场景**：高冲突热点（秒杀/集中转账，同一行每秒几百次写，乐观重试会空转）；"读-判断-写"复合操作（余额≥X 才允许扣）；强一致扣减
- **进阶切换策略**：先乐观，冲突重试超限 → 降级悲观（`SELECT ... FOR UPDATE` 重读重做）
- **注意**：FOR UPDATE 多行加锁顺序不一致会死锁；锁持有到事务结束——事务必须短
