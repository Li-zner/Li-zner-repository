# 分布式锁与乐观锁 学习笔记

> 学习目标：讲清楚"并发改余额为什么出错、三种武器分别是什么、我们支付系统的双锁怎么配合、刚修的三个 bug 是什么"。
> 对应代码：`app/payment/service.py`（`_acquire_lock` / `_release_lock` / `_do_update_balance` / `_apply_balance_change`）。

## 一、要解决的问题：竞态条件

两个请求同时给同一钱包加 100 元，余额从 0 开始：

```
请求A: 读余额=0 → 计算 0+100=100 → 写回 100
请求B: 读余额=0 → 计算 0+100=100 → 写回 100
最终余额 = 100   （应该是 200！）
```

这就是**竞态条件（Race Condition）**：操作交错执行，后写覆盖先写，丢了一次更新。

## 二、三种武器

| 武器 | 思路 | 类比 | 适用场景 |
|---|---|---|---|
| 悲观锁 | 先锁住再操作，谁都不许动 | 进厕所锁门 | 冲突多、写多 |
| 乐观锁 | 不锁，写时检查版本 | 保存前发现别人改过 | 冲突少、读多写少 |
| 分布式锁 | 多台机器共享一把锁 | 多食堂共用一个储物柜 App 抢锁 | 多实例环境 |

## 三、分布式锁（Redis 实现）

```python
async def _acquire_lock(key, ttl=10):
    token = uuid.uuid4().hex          # 唯一钥匙牌
    ok = await r.set(f"lock:{key}", token, nx=True, ex=ttl)
    return token if ok else None
```

三个核心机制：

1. **`nx=True`（Not eXists）**：key 不存在才写入成功 → 只有一个人能拿到锁
2. **`ex=ttl`（过期时间）**：锁自动过期 → 防止持锁者崩溃后锁永不释放
3. **`token`（唯一令牌）**：释放时校验身份 → 防误删他人锁

**释放锁的正确姿势（Lua 原子操作）**：

```python
# 只有钥匙牌对得上才删除
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
```

**为什么必须带令牌校验**：否则出现——A 拿锁，操作超时锁过期；B 拿锁；A 晚归执行 delete 把 B 的锁删了，C 又进来，三人同时操作。

## 四、乐观锁（version 字段 / CAS）

```python
UPDATE user_wallets SET balance = balance + $1,
       version = version + 1
WHERE user_id = $2 AND version = $3   -- 版本对不上 = 0 行更新
```

- **CAS（Compare-And-Swap）**：先读 version=5，更新时要求"当前还是 5"才更新
- 冲突时 UPDATE 影响 0 行 → 重读重试
- 不阻塞、无锁，适合读多写少；高冲突场景会频繁重试

## 五、为什么"双锁"都有（纵深防御）

| 锁 | 管什么 | 何时靠它 |
|---|---|---|
| 分布式锁 | 防止"同时进门" | 同一订单/钱包的并发操作（业务层） |
| 乐观锁 | 防止"出门时发现被改" | 锁过期、或多订单并发改同一钱包（数据层） |

分布式锁挡住 99% 并发进入；万一漏进来，乐观锁在数据库层兜底——要么成功要么明确失败。

## 六、刚修的三个 bug（实战回顾）

1. **误删他人锁** → 令牌 + Lua 条件删除
2. **冲突直接失败** → 自动重试 3 次（`_apply_balance_change`）
3. **扣费不检查冲突**（最严重）→ 原来并发扣费时余额没更新但流水照记、账会错；现在加用户级锁 + 检查更新结果，冲突安全跳过

## 七、面试问答

**Q: 分布式锁的缺点？**
> 锁可能过期（操作超时）；无法重入；Redis 主从切换可能丢锁（Redlock 方案解决）。

**Q: 乐观锁什么场景不合适？**
> 高冲突场景频繁重试，此时悲观锁或队列更合适。

**Q: 为什么不用数据库 `SELECT ... FOR UPDATE`？**
> 可以，那是数据库行锁（悲观锁），但占连接、锁时间长；Redis 锁更轻量。生产常两者结合。

## 八、延伸：锁与事务

- 分布式锁：业务层并发控制，跨实例生效
- 数据库行锁：数据层并发控制，同库生效
- 事务（BEGIN/COMMIT）：保证"多个操作要么全成要么全败"，与锁互补
- 生产规范：**先拿锁 → 起事务 → 读写 → 提交 → 释放锁**；顺序反了会出现死锁/数据不一致
