风险：payment_orders 包含 body TEXT 和 metadata JSONB，在分页列表场景下，这些大字段徒增网络传输和内存消耗。当订单量达百万级，查询会明显变慢。

修复：仅 SELECT 列表展示必需的 10 个核心字段（如 order_no, user_id, amount, status, created_at），详情接口再查全部。

38. 【P2】Redis 订单序列号 Key 无限增长，内存泄漏
文件：service.py – _generate_order_no，_ORDER_SEQ_KEY = "payment:order_seq"

风险：该 Key 使用 INCR 自增，从未设置过期时间，会无限增长。虽然每个 Key 只占几十字节，但运行数年也会累积，且无法清理（清理会导致订单号冲突）。

修复：改用按日期分 Key（如 payment:order_seq:20260818），每日自动过期或允许重复（日期+序列保证唯一）。

39. 【P2】get_channels 若 DB 表被误删，会静默返回硬编码默认值，掩盖异常
文件：service.py – get_channels

风险：if rows: 返回 DB 配置，else: 返回硬编码列表。若 DBA 误截断 payment_channels 表，接口依然返回“可用渠道”，运维无感知，直到渠道开关无法远程控制。

修复：如果 DB 表无数据，应抛出异常或记录 Error 日志，而非静默降级到硬编码（硬编码只可用于应用启动时的兜底初始化）。

40. 【P2】退款请求 amount 缺少 gt=0 校验，可传 0 造成无效退款单
文件：models.py – RefundRequest，service.py – process_refund

风险：RefundRequest.amount 为 Optional[Decimal]，无 gt=0 约束。若调用方传入 0，process_refund 中 refund_amount = 0，会成功创建一笔金额为 0 的退款订单，并写入流水，污染数据报表。

修复：在 Model 层增加 Field(gt=0)，并在 Service 层显式校验。
全新 P0 级：锁顺序死锁（Lock Ordering Deadlock）—— 连接池耗尽 + 分布式锁互相等待
文件：service.py – process_recharge 和 deduct_token_cost

代码顺序（致命错误）：

python
# process_recharge 逻辑顺序
1. lock_token = await _acquire_lock(lock_key)   # 先获取 Redis 分布式锁
2. pool = await get_pool()
3. async with pool.acquire() as conn:           # 再尝试获取数据库连接
死锁场景：

请求 A 处理订单 O1，已获取 Redis 锁 order:O1，此时数据库连接池已满（全部 20 个连接被其他慢查询占用）。请求 A 阻塞在 pool.acquire() 上，无法进入 finally 释放 Redis 锁。
请求 B 处理另一个订单 O2，幸运地拿到了一个空闲数据库连接，但执行过程中需要竞争同一把 Redis 锁（例如操作同一用户钱包或同一订单）。请求 B 阻塞在 _acquire_lock 上。
更糟糕的是：如果那 20 个被占用的连接恰好都在执行 process_recharge 且都持有着自己的 Redis 锁，那么所有工作线程都在等待 pool.acquire()，而外部所有新请求都在等待 Redis 锁释放。系统进入全局限死，无任何请求能继续，直到 TCP 超时或连接池强制回收。
修复（架构铁律）：必须先获取数据库连接，再获取分布式锁。将 pool.acquire() 移到 _acquire_lock 之前，确保连接在手后再抢锁。或者，pool.acquire() 必须设置强制超时（如 2 秒），超时后立即释放锁并返回 503。

🟡 全新 P1 级：Decimal 转 float 的审计精度灾难
文件：几乎全部 _order_to_dict、get_wallet、get_admin_stats

代码："amount": float(row["amount"])

风险：虽然金额较小（< 1000 元）时 float 精度误差在分位以下，但金融对账系统要求绝对精确。当金额涉及 0.01 * 0.01 的累计或千分位手续费时，float 二进制表示会引入 0.0000000001 级别的误差。虽然显示为浮点数没问题，但如果前端或报表系统拿这些 float 再次累加（如月度汇总），长期会累积出几毛钱的差异，导致对账不平。

修复：API 响应中金额字段应统一使用 字符串（str） 返回，如 "amount": "100.00"。前端保持字符串展示，后端计算始终用 Decimal。

🟡 全新 P1 级：管理端对账使用 DATE(created_at) 导致索引失效
文件：admin_routes.py – api_admin_reconcile

代码：WHERE DATE(created_at) = $1

风险：对 created_at 字段使用 DATE() 函数包裹，PostgreSQL 将无法使用普通 B-Tree 索引（idx_po_created），必须全表扫描。当日订单量超过 10 万时，该接口会严重拖慢数据库。

修复：改为范围查询：WHERE created_at >= $1 AND created_at < $2（其中 $1 为今日 00:00，$2 为明日 00:00）。这样索引生效，查询毫秒级。

🟢 全新 P2 级：ORDER BY created_at DESC 未与 user_id 形成复合覆盖索引，分页有性能衰减
文件：service.py – get_order_list

当前索引：CREATE INDEX idx_po_user ON payment_orders(user_id, created_at DESC)

风险：查询 WHERE user_id = $1 ORDER BY created_at DESC LIMIT 20 OFFSET 1000，虽然索引能按 user_id 过滤，但 OFFSET 较大时（如第 50 页），数据库需要扫描该用户的前 1000 条索引项再丢弃，深度分页性能差。

修复：使用 “游标分页”（Seek Method），即 WHERE user_id = $1 AND created_at < $last_created_at ORDER BY created_at DESC LIMIT 20，对于历史订单列表体验更好。

🧠 极深水下的隐匿风险（设计权衡，非代码错误）
41. 模拟支付状态下，processing 状态形同虚设
在事务中先将订单置为 processing，立即调用 channel.pay（模拟耗时 1-3 秒），成功后更新为 success。

隐忧：如果应用在 processing 更新后、channel.pay 返回前被强制重启（kill -9），事务因连接断开而回滚，订单状态会恢复为 pending（因为未提交）。这在理论上没问题。但若重启发生在 channel.pay 返回且事务提交的一瞬间（极低概率），订单可能停留在 processing 且无法自动恢复。虽然概率极低，但真正的生产级设计应引入定时任务扫描超时 processing 订单进行核对或冲正。
