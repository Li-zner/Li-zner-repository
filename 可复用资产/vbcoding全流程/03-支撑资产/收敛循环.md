# 收敛循环（实现 → 对照 → 补任务 → 再实现）

> **用途**：定义「一次做不对是常态」的迭代协议——实现后必须对照需求库找缺口，缺口变成任务再实现，
> 循环直到收敛，才允许进入下一功能（小循环）或代码审阅（大循环）。
> **何时用**：每个功能实现后（小循环）；全部功能完成后、进入审阅（`../02-任务-prompt/审阅-prompt.md`）前（大循环）。
> **来源**：GitHub spec-kit 的 implement/converge 收敛思想与 analyze 一致性检查，本地化。

## 1. 为什么需要收敛循环

- AI 一次生成的代码与需求有偏差是常态，不是例外；流程必须按「循环对齐」设计，而不是按「一次通过」设计
- 缺口不可见才会烂尾：必须显式输出「缺口清单」，而不是写完就当完成
- 收敛是客观状态：验收标准逐条可断言且全部通过即为收敛；不是「感觉差不多了」

## 2. 小循环（每个功能，内嵌于编码-prompt 第四步）

1. **实现**：按功能清单做当前这一个功能（纵向切片：一条用户路径）
2. **对照**：拿该功能关联的验收标准逐条自测（跑命令 / 断言 / 行为验证）
3. **缺口清单**：列出未满足项与计划外发现（需求没覆盖但「好像需要」的，只登记不实现）
4. **补任务**：每个缺口变成明确任务（改哪个文件、改成什么样、怎么验证）
5. **再实现**：执行补任务，回到第 2 步
6. **收敛标志**：该功能验收标准全部通过、无未处理缺口 → 勾选功能清单，进下一个功能

## 3. 大循环（全部功能完成后，进入审阅前）

1. **全量对照**：把需求库验收标准与 MVP 清单整体过一遍（不只逐功能，还要看功能间组合行为）
2. **一致性检查**：需求 ↔ 架构图谱 ↔ 协议 ↔ 验收标准交叉核对，矛盾与缺失列入缺口
   （对应 spec-kit 的 analyze：跨文档一致性检查，缺口不只藏在代码里，也藏在文档之间）
3. **缺口 → 任务 → 实现 → 复测**（同小循环第 3-5 步）
4. **收敛标志**：验收全过、一致性检查无未处理项、功能清单全勾 → 进入审阅（`../02-任务-prompt/审阅-prompt.md`）

## 4. 纪律

- 每轮循环必须输出「缺口清单」，禁止跳过对照直接宣称完成
- 同一缺口修 3 轮仍未收敛 → 停下问人（大概率是需求或方案有问题，不是代码问题）
- 计划外发现只登记不实现（需求边界见 `边界约束.md` 第 1 节）
- 审阅阶段发现的 P0/P1，修复后同样走「对照 → 复测 → 收敛」才算闭环
- 与需求库的关系：循环中若发现验收标准本身有误 → 停下问人，人确认后回写需求库，AI 无权改
