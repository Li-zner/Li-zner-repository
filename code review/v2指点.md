P0 级（必须立即修复，否则可能造成生产事故）
1. UPLOAD_DIR 依赖当前工作目录 (CWD)
位置：~L177

代码：UPLOAD_DIR = str(Path(os.path.abspath("uploads")))

风险：systemd/K8s 启动时 CWD 不确定，文件可能写入 /uploads（权限报错）或容器临时目录，重启后丢失；且在 extract_text_content_async 中通过 os.path.join(UPLOAD_DIR, f"{file_id}{ext}") 拼接，若目录不存在虽创建了，但路径错误会导致跨部署无法共享。

修复：基于 __file__ 绝对路径。

2. os.remove 未捕获 FileNotFoundError
位置：~L234（文本提取失败分支）

代码：await loop.run_in_executor(None, lambda: os.remove(save_path))

风险：并发请求删除同一文件，或文件已被外部清理，直接抛出异常导致 500 响应。

修复：包裹 try/except FileNotFoundError。

3. persona.system_prompt.format() 可能抛出 KeyError
位置：~L490

代码：system_content = persona.system_prompt.format(today=today_str, name=persona.name)

风险：数据库中若有人格模板缺少 {today} 或 {name}，该请求直接崩溃。

修复：用 try/except 兜底，或改用 string.Template 安全替换。

4. 文件提取的 text_content 无大小限制直接存入 Redis
位置：~L252

代码：await r.setex(f"file:{file_id}:content", 3600, text_content)

风险：20MB PDF 解析出 10MB+ 文本，攻击者上传几十个大文件瞬间打爆 Redis 内存。

修复：强制截断至 200KB（足够 LLM 理解），并记录截断日志。

5. 任务幂等键未包含 username，可能导致串号
位置：~L1075

代码：existing = await try_idempotent(req.session_id, req.message)

风险：若两个不同用户使用相同 session_id（如客户端默认 "default"）和相同消息，后一个请求会复用前一个用户的任务 ID，返回他人的生成结果。

修复：幂等键组合改为 f"{username}:{session_id}:{msg_hash}"。

6. /resume 恢复任务时未传递 persona_id 和 file_ids
位置：~L1160

代码：run_agent_task 仅传了 session_id、user_message、user_location

风险：用户取消“民法典人格+上传合同”的任务后恢复，变成默认人格且丢失文件，答非所问。

修复：在 task 存储中保留这两个字段，透传恢复。

7. GET /chat/tasks/{task_id}/result 的 wait 参数被硬编码 60s 覆盖
位置：~L1115

代码：deadline = time.time() + 60（完全忽略入参 wait）

风险：调用方传 wait=2 期望快速超时，实际阻塞 60 秒，导致前端请求堆积。

修复：max_wait = min(wait, 60) if wait > 0 else 0。

8. ALLOWED_EXTENSIONS 包含 .py、.js、.env 等源码文件
位置：~L185

代码：{'.py', '.js', '.env', ...}

风险：用户上传 app/main.py 或 .env，内容被截断 50000 字符后送入 LLM，导致业务源码/数据库密码可能泄露给第三方 API。

修复：生产环境移除所有源码类和密钥类扩展名，或限制仅 admin 角色可上传。

9. asyncio.as_completed 超时后未取消仍在运行的子任务（多 Agent 快速通道）
位置：~L750

代码：for _done in asyncio.as_completed(..., timeout=TOOL_TIMEOUT):

风险：超时后仅补了空结果，僵尸协程继续占用 Redis/HTTP 连接池直到自然结束，高并发下连接耗尽。

修复：except TimeoutError: 中显式遍历并 task.cancel()。

10. 主 ReAct 循环中 asyncio.wait_for 超时也未取消任务
位置：~L920

代码：tool_results = await asyncio.wait_for(asyncio.gather(...), timeout=TOOL_TIMEOUT)

风险：同上，asyncio.gather 中的任务在超时后不会被自动取消（wait_for 取消的是 gather 本身，但 gather 默认不会取消子任务，需传 return_exceptions=False 才会传播取消，而此处为 True）。

修复：在 except TimeoutError 中遍历 tasks 列表逐个 cancel()。

11. SemanticCache.set_empty 使用 asyncio.create_task 导致生命周期悬空
位置：~L531（以及 ~L425）

风险：若客户端断开触发 CancelledError，该后台任务可能被事件循环丢弃，缓存未写入，后续请求持续击穿。且 create_task 不等待，违反“防击穿”锁的原子性预期。

修复：改为 await SemanticCache.set_empty(...)，或绑定到 BackgroundTasks。

12. Key 轮询每次请求都调用 os.getenv（3 次系统调用）
位置：~L160

风险：高 QPS 下积累 CPU 开销，且若运维热更新 Key，轮询列表在迭代中可能变化（虽概率低，但非原子）。

修复：模块启动时缓存到全局列表，提供 reload_keys() 管理接口。

13. _get_deepseek_key 使用 random.choice 无健康剔除
位置：~L165

风险：若某个 Key 已限流/失效，随机轮询仍可能选中，导致失败率居高不下（加权轮询或记录失败次数的平滑加权更优）。

修复：改用带权重的 Round Robin，并动态剔除连续失败的 Key。

14. 流式推理的敏感词过滤效率极低（any(p in low for p in patterns)）
位置：~L118、~L140（_sanitize_reasoning / _clean_reasoning）

风险：每个流式 Chunk（每秒上百个）遍历 50+ 个字符串，CPU 消耗显著；且 _sanitize_reasoning 和 _clean_reasoning 存在冗余双过滤（三套关键词数组），维护成本高。

修复：合并为单一预编译正则（re.compile('|'.join(patterns))）或 Aho-Corasick。

15. _lang_instruction 在单次请求中被多次调用，重复构建字符串
位置：~L85，在 L500、L680、L830 等多处调用

17. 法律映射表拦截 return 早于 saved_normally = True
