# 修复 Bug Prompt（任务类型：修 Bug）

> **用途**：修复一个症状明确的 Bug 时的任务入口。与编码任务的本质区别：目标是「恢复需求库定义的正确行为」，
> 不新增功能、不重构、不顺手优化。
> **何时用**：`../AGENTS.md` 路由到「修 Bug」时读本文件。
> **前置**：底层规则已读；本项目需求库已存在（没有需求库就无所谓 Bug——先走需求库流程）。

## 使用前准备（人类做）

1. 提供症状：现象、复现步骤、期望行为 vs 实际行为
2. 指出相关需求文件路径（验收标准是「对不对」的唯一判据）

## 可复制 Prompt

```
你是一名资深工程师，负责修复项目 <项目名> 的 Bug <编号/简述>。

【第一步：读需求，先判性质】
1. 先读并全程遵守底层规则 `../00-底层规则/底层规则.md`；本任务额外读 <../03-支撑资产/边界约束.md>
2. 读需求文件中与本 Bug 相关的需求与验收标准——这是「正确行为」的唯一判据
3. 若「正确行为」需求库没有定义 → 这不是 Bug 而是未定义行为：停下问人，禁止按猜测修

【第二步：复现优先】
1. 先做出最小可复现（命令 / 测试用例 / 操作步骤），白纸黑字写下来
2. 复现不出来 → 停下，说明已尝试什么、需要什么信息；禁止「大概修好了」

【第三步：定位根因】
1. 用一句话说清根因：哪个假设错了、哪个边界漏了，为什么会走到这一步
2. 禁止只抹症状（catch 吞异常、调阈值掩盖、改 UI 藏错误）
3. 根因不在本仓库 → 给出证据链，向人汇报，不擅自动外部系统
4. 方法论（借鉴 superpowers systematic-debugging）：根因追踪——从症状反向追到第一因，不在半路停下；
   纵深防御（defense-in-depth）——单点修复不稳时加一层校验兜底；
   条件等待（condition-based-waiting）——异步/时序问题等条件成立，禁止固定 sleep

【第四步：最小修复】
1. 只改与根因相关的代码；发现顺手可重构/可优化处 → 登记不做
2. 涉及结构级改动时读 <../03-支撑资产/编码规则.md 路径>，同样遵守
3. 把复现用例固化为回归测试；跑相关全量测试，确认无副作用

【第五步：收敛与汇报】
1. 对照该功能验收标准复测（小循环见 <../03-支撑资产/收敛循环.md>）
2. 汇报：根因一句话 / 改动清单 / 测试证据 / 影响面（还有谁依赖这段代码）
3. 改动涉及并发/事务/安全/协议，或净增超过 50 行 → 走 <审阅-prompt.md> 审阅后才算完成
```

## 与编码任务的差别（速查）

| | 编码（编码-prompt） | 修 Bug（本文件） |
|---|---|---|
| 目标 | 实现新功能 | 恢复需求库定义的既有行为 |
| 起点写骨架 | 是 | 否，从复现开始 |
| 改动范围 | 纵向功能切片 | 根因最小集 |
| 必读支撑 | 架构规则 + 边界约束 + 编码规则 + 收敛循环 | 边界约束 + 收敛循环（涉及结构加编码规则） |
| 产出 | 功能 + 测试 | 根因说明 + 回归测试 |

## 常见坑

- **两个 Bug 一起修**：一次只修一个；修第二个前先确认第一个的回归测试还绿
- **修出新 Bug**：改动前记录影响面（谁调用这段代码），修完跑调用方测试
- **需求没写的行为**：不是 Bug，走需求变更（人确认后回写需求库），再回来修
