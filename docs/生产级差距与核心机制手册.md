# 第四部分：核心机制——代码·原理·正确用法·为什么

## 机制 1：认证（JWT）

**你的代码**（`auth.py`）：

```python
def create_access_token(data: dict):
    to_encode = data.copy()
    now = datetime.utcnow()
    expire = now + timedelta(days=ACCESS_TOKEN_EXPIRE_DAYS)  # 7 天
    to_encode.update({"exp": expire, "iat": now})
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)  # HS256
```

**核心原理**：JWT 是无状态票据——服务器不存会话，验签即验真。`exp`（过期）、`iat`（签发时间）是标准字段，HS256 用密钥签名防伪造。

**正确用法**：

- access token 应短（15min~2h）+ refresh token 长（7~30 天）可轮换
- 密钥强度高、多版本轮换（kid 标识）、缺失即拒绝启动
- 校验 `iss`/`aud`/`exp`/`jti`

**为什么这样做**：

- 短 access + 可吊销 refresh = 泄露面最小（token 泄露攻击者只能用 15 分钟）
- 无状态 = 多实例天然适配（任何实例验签即验真，不用共享会话存储）
- 代价是"无法主动踢人"，所以企业要配 jti 黑名单

## 机制 2：限流（固定窗口）

**你的代码**（`rate_limit.py`）：

```python
async def check_qps(username, role="user"):
    key = f"qps:{username}:{int(time.time())}"   # 每秒一个 key
    count = await r.incr(key)
    if count == 1:
        await r.expire(key, 2)
    return count <= limits["qps"]
```

**核心原理**：固定窗口——把时间切成固定秒数，每个窗口一个计数器，窗口内超限即拒绝。

**边界缺陷**：窗口切换瞬间可能双倍流量。例：限 10/s，第 1 秒末放行 10 个，第 2 秒初又放行 10 个——1 秒内实际放了 20 个。

**正确用法（生产级）**：

- **滑动窗口**：按时间戳记录每次请求，统计"最近 N 秒"的请求数，消除边界双倍
- **令牌桶**：匀速放 token，允许突发但平均受限（适合聊天这类有突发特性的场景）
- **漏桶**：恒定速率输出，平滑但不允许突发

**为什么这样做**：限流的目标是"保护后端 + 公平"，固定窗口实现简单（Redis INCR 一个 key）但边界有漏洞；企业接口常叠加：网关层（IP 级，防 DDoS）+ 应用层（用户级，防滥用）+ 配额层（成本控制）。

## 机制 3：熔断

**你的代码**（`circuit_breaker.py`）：

```python
class SimpleBreaker:
    def __init__(self, fail_threshold=3, recover_timeout=30):
        self.state = "CLOSED"   # CLOSED / OPEN / HALF_OPEN
    async def call(self, async_func, *args, **kwargs):
        if self.state == "OPEN":
            if time.time() - self.last_fail_time > self.recover_timeout:
                self.state = "HALF_OPEN"
            else:
                raise Exception("熔断器已开启")
        try:
            result = await async_func(*args, **kwargs)
            if self.state == "HALF_OPEN":
                self.state = "CLOSED"
            return result
        except Exception:
            self.fail_count += 1
            if self.fail_count >= self.fail_threshold:
                self.state = "OPEN"
            raise
```

**核心原理**：三态状态机——连续失败达阈值 → OPEN（快速失败，不浪费连接）；过恢复期 → HALF_OPEN（放一个试探请求）；试探成功 → CLOSED。按端点隔离（注册表）防止"一个接口拖死全部"。

**正确用法**：

- 与**超时**搭配（先超时，超时也算失败）
- 与**降级**搭配（熔断后返回兜底结果而非报错）
- 按端点/下游拆分，不要全局一个熔断器

**为什么这样做**：下游故障时，如果所有请求都傻等超时，连接池会被占满、整个系统假死。熔断是"快速失败"，牺牲单次可用性换取整体不雪崩。

## 机制 4：分布式锁（本轮修复）

**你的代码（修复后）**（`service.py`）：

```python
async def _acquire_lock(key, ttl=10):
    token = uuid.uuid4().hex
    ok = await r.set(f"lock:{key}", token, nx=True, ex=ttl)
    return token if ok else None

# Lua：值匹配才删除（原子）
_RELEASE_LUA = """
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
"""
async def _release_lock(key, token):
    await r.eval(_RELEASE_LUA, 1, f"lock:{key}", token)
```

**核心原理**：`nx=True` 保证只有一个持有者；`ex=ttl` 防持锁者崩溃后死锁；`token` 保证释放时校验身份。

**正确用法**：

- **必须带唯一令牌**（否则有误删他人锁的 bug，我们踩过）
- TTL 要大于最长操作时间；操作可能超时则要**看门狗续期**
- 释放必须用 Lua（检查+删除原子化），不能先 get 再 delete（中间有窗口）

**为什么这样做**：误删他人锁 = 并发保护失效 = 资金/数据错误。原子性（Lua）和身份校验（token）是分布式锁的正确姿势。

## 机制 5：乐观锁（本轮修复）

**你的代码（修复后）**（`service.py`）：

```python
async def _apply_balance_change(conn, user_id, delta, max_retries=3):
    for _ in range(max_retries + 1):
        row = await conn.fetchrow("SELECT balance, version FROM user_wallets WHERE user_id=$1", user_id)
        updated = await _do_update_balance(conn, user_id, delta, row["version"])
        if updated:
            return True, row["balance"], row["balance"] + delta, row["version"]
    return False, None, None, None

# _do_update_balance 核心：
# UPDATE user_wallets SET balance = balance + $1, version = version + 1
# WHERE user_id = $2 AND version = $3   -- 版本对不上 = 0 行
```

**核心原理**：CAS（Compare-And-Swap）——读时记版本，写时要求"版本还是我读的那个"才更新。影响 0 行 = 冲突 = 重读重试。

**正确用法**：

- 冲突重试**必须有上限**（防止极端竞争下无限空转）
- **必须检查 UPDATE 结果**——不检查就像我们原来的 bug：冲突时余额没更新但流水照记，账目错误
- 适合低冲突场景；高冲突用悲观锁/队列

**为什么这样做**：乐观锁不阻塞、无锁开销，适合"读多写少"。但"检查结果"和"有界重试"是它的两条安全线，缺一不可。

## 机制 6：语义缓存

**你的代码**（`semantic_cache.py`）：

```python
# L2 语义匹配（pg_trgm）
SELECT id, response, similarity(query_text, $1) AS sim
FROM semantic_cache
WHERE similarity(query_text, $1) > 0.85
ORDER BY sim DESC LIMIT 1
```

**核心原理**：三级金字塔（内存 LRU → 精确哈希 → 语义相似度），命中逐级回填，越用越快。阈值 0.85 = "宁可 miss 不可错配"。

**正确用法**：

- 相似度阈值要按场景调：问答类可高（0.85+），检索类可低
- 注意**缓存一致性**：L0 是进程内存，清库不清内存（要重启）
- 生产要防**击穿**（热点 key 失效瞬间全打后端）→ 互斥重建；防**雪崩**（大量 key 同时失效）→ 随机过期

**为什么这样做**：省 token = 省钱（LLM 按 token 计费）。但缓存引入一致性和击穿问题，生产级要补防护。

## 机制 7：冷热分层记忆

**你的代码**（`memory_manager.py`）：

```python
_PG_WRITE_SEMAPHORE = asyncio.Semaphore(5)  # 最多 5 个并发写 PG

async def save_messages(self, user_msg, assistant_msg):
    # 先写 Redis（立即生效）
    await redis.rpush(history_key, ...)
    # 再异步写 PG（不阻塞主流程）
    asyncio.create_task(self._save_to_pg(user_msg, assistant_msg))

async def _save_to_pg(self, ...):
    async with _PG_WRITE_SEMAPHORE:   # 限流，防连接池耗尽
        ...
```

**核心原理**：热数据（最近对话）存 Redis 毫秒取回，冷数据（历史）存 PG 持久；写 Redis 同步 + 写 PG 异步。

**正确用法**：

- 异步落盘要**信号量限流**（防高并发下写库占满连接池拖死主流程）
- 异步任务要**异常兜底**（写失败不能影响主流程）
- 生产要考虑**失败补偿**（异步丢了怎么办 → 补偿任务/对账）

**为什么这样做**：同步写 PG 在高并发下是主流程的瓶颈；异步化 + 限流是"既快又不拖垮"的平衡。

## 机制 8：RAG 双通道检索

**你的代码**（`tools.py`）：

```python
# 第一阶段：pg_trgm 关键词召回
# 第二阶段：DeepSeek Rerank 精排
candidates = await _rerank_with_deepseek(query, candidates, top_k)
```

**核心原理**：召回（Recall）阶段用关键词+向量双通道多取候选（求全），精排（Rerank）阶段重排取 top_k（求准）。召回求全、精排求准，两段式控制质量与成本。

**正确用法**：

- 关键词通道兜底"专业术语"，向量通道理解"语义近义"
- Rerank 只对 top_k 候选精排（全量精排太贵）
- 回答带出处（法条引用）——可追溯、可验证

**为什么这样做**：单通道会漏（关键词漏语义、向量漏术语）；Rerank 在"精确"和"成本"之间取平衡。RAG 的核心是"检索质量决定回答质量"。

## 机制 9：支付幂等

**你的代码**（`process_recharge`）：

```python
lock_key = f"order:{order_no}"
lock_token = await _acquire_lock(lock_key)
if not lock_token:
    raise ValueError("订单正在处理中，请勿重复提交")
...
if order["status"] != "pending":
    raise ValueError(f"订单状态不允许支付: {order['status']}")  # 状态机防重入
```

**核心原理**：幂等 = 同一操作重复执行结果相同。两层防护：分布式锁（并发防重入）+ 订单状态机（pending→success 只能走一次）。

**正确用法**：

- 每个资金操作都要"天然幂等"（同订单号重复请求不重复扣款）
- 真实支付还要：回调**签名验签**、回调重试幂等、对账兜底
- 关键字段加**唯一约束**（如订单号）

**为什么这样做**：用户点两下、渠道重试回调、网络重发——没有幂等就会重复扣款，这是资金事故级别的问题。

## 机制 10：滚动发布与回滚

**你的代码**（`ci.sh`）：

```bash
for svc in gateway gateway2 gateway3 gateway4; do
    docker compose up -d --no-deps --force-recreate "$svc"
    wait_healthy "$container" "$port" || { rollback "$PREV_IMAGE"; exit 1; }
done
```

**核心原理**：一次只升级一个实例，健康检查通过才动下一个；任何一步失败回滚到上一个镜像。零停机。

**正确用法**：

- 发布前记录当前镜像（`PREV_IMAGE`）→ 失败能回滚
- 冒烟测试（登录/health）作为发布成功的判定
- 灰度更细：先 1 台验证 → 再全量

**为什么这样做**：全量重建 = 上线瞬间全站停摆（旧方式 `--force-recreate` 4 个一起）。滚动发布牺牲一点部署时间，换来"用户无感知"。

## 机制 11：数据库版本化迁移

**你的代码**（`alembic/versions/76a1f09d2ac8_baseline_schema.py`）：

```python
def upgrade():
    op.execute("CREATE TABLE IF NOT EXISTS users (...)")

def downgrade():
    op.execute("DROP TABLE IF EXISTS users CASCADE")
```

**核心原理**：表结构变更像代码一样有版本号（revision）、可升级（upgrade）可回退（downgrade），`alembic_version` 表记录当前版本。

**正确用法**：

- 新增表/列一律写迁移，不手敲 SQL
- 迁移要**幂等**（IF NOT EXISTS）
- 上线前在临时库验证迁移（我们做了：`agent_gateway_test` 完整跑通）

**为什么这样做**：手动改表没有记录，线上库和代码永远对不上，改坏了无法回滚——数据库迁移是"结构变更的可回滚性"。

## 机制 12：SLO 与告警

**你的代码**（`alert.rules.yml`）：

```yaml
- alert: HighErrorRate
  expr: (sum(rate(gateway_requests_total{status=~"5.."}[5m])) / sum(rate(gateway_requests_total[5m]))) > 0.05
  for: 1m
```

**核心原理**：SLI（怎么测）→ SLO（目标数字）→ 告警（超阈值通知）。用数字定义"健康"。

**正确用法**：

- 错误率、p95 延迟、缓存命中率、token 成本都要有告警
- 告警要有 `for`（持续多久才触发，防抖动误报）
- 告警后要有**处置 SOP**（查 Grafana → 查 Tempo → 查 Loki）

**为什么这样做**："还行吧"无法管理；数字 + 告警让劣化在用户投诉前被发现。可观测的终点是"能快速定位 + 能自动通知"。

## 机制 13：异步编程与事件循环（asyncio）

**你的代码**（`orchestrator.py`）：

```python
# asyncio.gather 并行调用多个 Agent
results = await asyncio.gather(
    agent_weather.call(query),
    agent_hotel.call(query),
    agent_route.call(query),
    agent_food.call(query),
)
```

**核心原理**：Python 的异步是**单线程 + 事件循环**。`await` 遇到 IO 等待时让出控制权，事件循环去执行其他协程，IO 完成后回来继续。`asyncio.gather` 同时启动多个协程，总耗时 = 最慢的一个，而不是相加。

**正确用法**：

- 只有 **IO 密集**（网络/数据库/文件）才用异步；CPU 密集要交给线程/进程池
- 协程里**不能有阻塞调用**（`time.sleep`、同步 requests）——会卡死整个事件循环
- 并发任务要设上限（信号量），防止一次性铺太多

**为什么这样做**：一个请求要等 4 次 LLM 调用（每次 2-5 秒），串行 = 20 秒，并行 = 5 秒。异步是 IO 密集服务的核心性能手段，也是你"800 并发"能扛住的根基（单线程事件循环能同时挂起成千上万个等待）。

## 机制 14：连接池（asyncpg）

**你的代码**（`db.py`）：

```python
pool = await asyncpg.create_pool(
    dsn=POSTGRES_DSN,
    min_size=20, max_size=50,  # 每个实例
)
```

**核心原理**：连接池是"预先建好、循环复用"的数据库连接集合。建连接很贵（TCP + 认证握手），池化后请求直接从池里拿，用完归还。

**正确用法**：

- `min_size`（常驻底线）与 `max_size`（峰值上限）按并发量估：4 实例 × 50 = 200 上限
- **获取连接用 `async with pool.acquire()`**（用完必还，防泄漏）
- 慢查询会"占住"连接——所以慢查询监控是连接池的第一保护

**为什么这样做**：没有连接池 = 每个请求新建连接 = 高并发下数据库被打爆（连接数爆炸）。有池 = 连接复用 + 超限排队。连接池是数据库高并发的第一道闸。

## 机制 15：数据库索引

**你的代码**（`alembic` 基线迁移）：

```sql
-- B-tree（默认）：范围查询
CREATE INDEX idx_po_created ON payment_orders USING btree (created_at);
-- GIN + trigram：模糊/相似度搜索
CREATE INDEX idx_kb_trgm ON knowledge_chunks USING gin (content public.gin_trgm_ops);
-- ivfflat：向量近似检索
CREATE INDEX idx_knowledge_embedding ON knowledge_chunks USING ivfflat (embedding public.vector_cosine_ops) WITH (lists='100');
```

**核心原理**：

- **B-tree**：默认索引，适合等值/范围/排序
- **GIN**：适合"元素是否包含"（数组、全文、trigram），pg_trgm 用它做模糊匹配
- **ivfflat**：向量近似的"倒排文件"索引，把向量聚类成 lists 个桶，检索只查相近的桶

**正确用法**：

- 索引不是越多越好——每个索引拖慢写入
- 用 `EXPLAIN ANALYZE` 验证是否走索引
- 向量索引要权衡**召回率 vs 速度**（lists 越大越准越慢）

**为什么这样做**：没有索引 = 全表扫描 = 数据量上来后查询从毫秒级退化到秒级。你的知识库检索、语义缓存相似度、订单查询都靠索引才快。

## 机制 16：事务与隔离级别

**你的代码**（`service.py` 资金操作）：

```python
async with conn.transaction():
    await _do_update_balance(...)      # 改余额
    await _do_record_tx(...)           # 记流水
# 提交成功 = 两个都生效；失败 = 两个都回滚
```

**核心原理**：事务保证 ACID——原子性（全成或全败）、一致性、隔离性、持久性。资金操作必须"改余额 + 记流水"一起提交，否则余额变了但没记录 = 账目不可对。

**正确用法**：

- 资金类操作：**先取锁 → 开事务 → 读写 → 提交 → 释放锁**
- 默认隔离级别（PG 是 Read Committed）适合大部分场景；需要防幻读用更高隔离
- 事务**要短**——长事务占连接、锁资源，是生产事故常见源

**为什么这样做**："余额变了但流水没记"或"流水记了但余额没变"都是资金事故。事务让多步操作成为不可分割的整体。

## 机制 17：SSE 流式

**你的代码**（`v2.py`）：

```python
async def stream_chat(...):
    yield f"data: {json.dumps({'type': 'answer_chunk', 'content': chunk})}\n\n"
```

**核心原理**：SSE（Server-Sent Events）是 HTTP 长连接——服务器持续往同一个响应里写 `data: ...\n\n` 格式的数据，浏览器逐段渲染。与 WebSocket 的区别：SSE 单向（服务器→客户端）、基于 HTTP、天然带重连。

**正确用法**：

- 流式必须**关缓冲**（nginx `proxy_buffering off`，否则攒一批才发）
- 客户端断连要**取消生成任务**（生产级必做，你还没做）
- 记录**首 token 时间**（TTFT）作为体验指标

**为什么这样做**：LLM 生成要 2-10 秒，等全部生成完再返回 = 用户盯着空白 10 秒；流式 = 打字机效果，首 token 1 秒内出现，体验天差地别。

## 机制 18：Nginx 负载均衡算法

**你的代码**（`nginx.conf`）：

```nginx
upstream gateway_cluster {
    server agent_gateway:10086 max_fails=3 fail_timeout=30s;
    server agent_gateway2:10086 max_fails=3 fail_timeout=30s;
    ...
}
```

**核心原理**：默认**轮询**（round-robin）轮流分发。`max_fails` + `fail_timeout` 是被动健康检查——连续失败 3 次，30 秒内不再派活给它。

**正确用法**：

- 服务端无状态（你的 JWT）→ 轮询即可，不需要 ip_hash
- 需要会话粘滞（有状态）才用 `ip_hash`；要按权重用 `weight`
- 要主动健康检查（实时探测）需要 nginx-plus 或额外探针

**为什么这样做**：轮询让 4 个实例负载均匀；被动健康检查让挂掉的实例自动摘除。这是"负载均衡 + 故障转移"的最小实现。

## 机制 19：容器化与镜像分层

**你的 Dockerfile**：

```dockerfile
FROM python:3.11-slim
COPY requirements.txt .
RUN pip install -r requirements.txt      # 依赖层
COPY app/ ./app/                          # 代码层
```

**核心原理**：镜像由**只读层**堆叠。每一条指令产生一层；构建时**层缓存**——某一层没变就复用。依赖层（pip install）在最上面 COPY 代码之前，所以"代码改了依赖没改"时只重建代码层。

**正确用法**：

- **先 COPY 依赖清单，再 COPY 代码**（让依赖层能缓存）
- 不要 `--no-cache` 全量重建（你踩过：每次重装 torch 20 分钟）
- 健康检查（HEALTHCHECK）让容器"自愈"

**为什么这样做**：层缓存是构建速度的关键；正确的 Dockerfile 顺序让"改一行代码 → 秒级构建"，错误顺序让"改一行代码 → 全量重装依赖"。

## 机制 20：Docker 网络

**你的部署**：

```yaml

  - docker_default   # 与 nginx 同网
```

**核心原理**：容器用**网络命名空间**隔离。`bridge` 网络内容器通过**服务名互相访问**（`postgres`、`redis` 是 DNS 名字）；对外用 `-p` 端口映射发布。

**为什么这样做**：服务名解析 + 网络隔离 = 容器重启 IP 变了也不影响互相调用；不发布端口 = 缩小攻击面。

## 机制 21：消息队列（MQ）

**为什么生产要 MQ**（你现在没有，是差距）：

```python
# 现在的做法：进程内 asyncio.create_task 异步
asyncio.create_task(self._save_to_pg(...))

# 生产级做法：发到队列，消费者异步处理
await redis.xadd("memory:write", {...})   # Redis Streams
# 或 RabbitMQ / Kafka
```

**核心原理**：MQ（消息队列）是"生产者-消费者"中间层——生产者发消息就走人，消费者慢慢处理。作用：**解耦**（两端互不知道）、**削峰**（突发流量先入队）、**异步**（主流程不等慢操作）、**可靠**（消息持久化，处理失败可重试）。

**正确用法**：

- 适合：异步写库、通知发送、任务分发、日志采集
- 不适合：需要立即响应的同步调用、强一致场景
- 轻量可选：Redis Streams（你已有 Redis）；重量级：RabbitMQ / Kafka

**为什么这样做**：`asyncio.create_task` 是"进程内异步"——进程重启任务就丢、多实例会重复。MQ 是"跨进程、可持久、可重试"的异步，是生产级异步的标配。

## 机制 22：缓存穿透/击穿/雪崩

**三个经典问题**：


| 问题 | 场景                         | 后果                        |
| ---- | ---------------------------- | --------------------------- |
| 穿透 | 查不存在的 key（如恶意构造） | 每次都打到 DB/LLM，缓存失效 |
| 击穿 | 单个热点 key 过期瞬间        | 大量请求同时打 DB/LLM       |
| 雪崩 | 大量 key 同时过期            | 缓存整体失效，DB 被打爆     |

**正确用法**：

- **穿透**：缓存空值（存空结果 + 短 TTL）；布隆过滤器
- **击穿**：**互斥重建**——同一时间只允许一个请求重建缓存，其他等待
- **雪崩**：**随机过期**（TTL 加随机抖动）；多级缓存

**你的差距**：语义缓存只有单点实现，没有互斥重建和随机过期。生产要补。

**为什么这样做**：缓存失效瞬间的流量风暴会打爆后端——这三个问题是大厂面试必考、线上必踩的经典。

## 模板 1：滑动窗口限流（Redis ZSET）

```python
async def sliding_window_limit(key: str, limit: int, window_sec: int = 60) -> bool:
    """滑动窗口限流：统计最近 window_sec 秒内的请求数"""
    r = await get_redis()
    now = time.time()
    pipe = r.pipeline()
    pipe.zremrangebyscore(key, 0, now - window_sec)   # 清掉窗口外的
    pipe.zadd(key, {str(uuid.uuid4()): now})          # 记录本次
    pipe.zcard(key)                                    # 统计窗口内数量
    pipe.expire(key, window_sec)
    results = await pipe.execute()
    return results[2] <= limit
```

**为什么**：修复固定窗口的"边界双倍流量"问题——ZSET 按时间戳排序，统计的是真实的最近 N 秒。

## 模板 2：令牌桶（Lua，原子）

```lua
-- key: 桶名, argv: 容量, 每秒速率, 当前时间
local tokens = tonumber(redis.call("get", KEYS[1]) or ARGV[1])
local last = tonumber(redis.call("get", KEYS[1]..":ts") or ARGV[3])
local now = tonumber(ARGV[3])
local refill = (now - last) * tonumber(ARGV[2])
tokens = math.min(tokens + refill, tonumber(ARGV[1]))
if tokens >= 1 then
    redis.call("set", KEYS[1], tokens - 1)
    redis.call("set", KEYS[1]..":ts", now)
    return 1
else
    return 0
end
```

**为什么**：令牌桶允许"突发但平均受限"——适合聊天这类有突发特性的场景；Lua 保证检查和扣减原子。

## 模板 3：分布式锁看门狗（续期）

```python
async def acquire_with_watchdog(key: str, ttl: int = 10) -> Optional[str]:
    token = uuid.uuid4().hex
    if not await r.set(f"lock:{key}", token, nx=True, ex=ttl):
        return None
    # 后台续期：每 ttl/3 秒续一次，直到主动释放
    task = asyncio.create_task(_renew_loop(key, token, ttl))
    return token

async def _renew_loop(key, token, ttl):
    while True:
        await asyncio.sleep(ttl / 3)
        # Lua：值匹配才续期（防续了别人的锁）
        renewed = await r.eval(RENEW_LUA, 1, f"lock:{key}", token, ttl)
        if not renewed:
            return  # 锁已不在（被释放或过期）
```

**为什么**：简单 TTL 锁在"操作超过 TTL"时会提前失效，两个请求并发进入。看门狗让"活着的人一直持有，死了的自动过期"。

## 模板 4：refresh token 轮换

```python
async def refresh_token(old_refresh: str) -> dict:
    payload = jwt.decode(old_refresh, SECRET_KEY, algorithms=[ALGORITHM])
    jti = payload.get("jti")
    # 1. 检查是否已被吊销（Redis 黑名单）
    if await redis.get(f"refresh:revoked:{jti}"):
        raise ValueError("refresh token 已被吊销")
    # 2. 作废旧 token（轮换）
    await redis.set(f"refresh:revoked:{jti}", "1", ex=REFRESH_MAX_DAYS * 86400)
    # 3. 签发新的 access + refresh（新 jti）
    new_access = create_access_token({"sub": payload["sub"], "type": "access"})
    new_refresh = create_refresh_token({"sub": payload["sub"], "jti": uuid.uuid4().hex})
    return {"access_token": new_access, "refresh_token": new_refresh}
```

**为什么**：轮换 = 每次刷新旧 token 立即作废——即使 refresh token 泄露，攻击者只能用它一次；发现可疑还能吊销。

## 模板 5：幂等中间件（HTTP 层）

```python
IDEMPOTENT_KEY_HEADER = "Idempotency-Key"

async def idempotent_handler(request: Request, call_next):
    key = request.headers.get(IDEMPOTENT_KEY_HEADER)
    if not key:
        return await call_next(request)
    # 检查是否处理过
    cached = await redis.get(f"idem:{key}")
    if cached:
        return JSONResponse(status_code=200, content=json.loads(cached))
    response = await call_next(request)
    # 缓存响应（含状态码），供重复请求直接返回
    if response.status_code < 500:   # 5xx 不缓存（允许重试）
        await redis.set(f"idem:{key}", json.dumps({...}), ex=3600)
    return response
```

**为什么**：前端重试、网络重发、渠道回调都可能导致同一请求发多次。幂等键让"重复请求返回第一次的结果"，不重复执行。

## 模板 6：FastAPI 断连取消

```python
@app.post("/v2/chat/stream")
async def stream_chat(request: Request):
    async def generate():
        task = asyncio.create_task(llm_stream(...))   # 后台生成
        try:
            while not task.done():
                # 每 0.2s 检查客户端是否断开
                if await request.is_disconnected():
                    task.cancel()                     # 断开就取消，省资源
                    return
                chunk = await asyncio.wait_for(task.__anext__(), timeout=0.2)
                yield f"data: {chunk}\n\n"
        except asyncio.CancelledError:
            task.cancel()
    return StreamingResponse(generate(), media_type="text/event-stream")
```

**为什么**：用户关页面后服务端还在跑 LLM 生成 = 白烧 token 和资源。断连取消是生产级流式接口的必备。

## 模板 7：缓存防击穿（互斥重建）

```python
import asyncio
_rebuild_locks: dict = {}

async def get_or_rebuild(key: str, rebuild_func):
    cached = await cache_get(key)
    if cached:
        return cached
    # 互斥锁：同一时间只允许一个重建
    lock = _rebuild_locks.setdefault(key, asyncio.Lock())
    async with lock:
        cached = await cache_get(key)          # 双检：等锁时别人可能已重建
        if cached:
            return cached
        value = await rebuild_func()
        await cache_set(key, value, ttl=random.uniform(300, 600))  # 随机过期防雪崩
    return value
```

**为什么**：热点 key 过期瞬间，100 个请求同时去重建 = 打爆后端。互斥重建让"只有一个请求真去重建，其他等待拿结果"。

## 用户完整旅程（大厂版全链路）

### 第一阶段：用户登录

**用户操作**：输入账号密码，点击登录。

**后端执行**：

1. 网关接收请求，查 PostgreSQL `users` 表校验密码（**数据库索引**加速 `WHERE username=?`）。
2. 校验通过，生成 JWT Access Token（短期，2 小时）和 Refresh Token（长期，7 天，带 `jti` 唯一标识）。
3. Refresh Token 的 `jti` 存入 Redis，用于后续**吊销和轮换**。
4. 返回 Token 给前端，前端后续所有请求携带 Authorization Header。

**涉及的机制**：JWT 认证（机制 1）、Token 轮换 + 吊销（机制 1 扩展）、数据库索引（机制 15）。

### 第二阶段：用户浏览商品 / 进入页面

**用户操作**：浏览商品列表、查看详情。

**后端执行**：

1. 网关验证 JWT（验签 + 检查是否过期）。
2. **限流器**检查该用户的 QPS 是否超限（四维限流：QPS/并发/日请求/日 Token，角色分级）。
3. 请求进入业务层：
   * 商品信息先从 **L1（Redis 精确缓存）** 读，命中直接返回。
   * 未命中则查 PostgreSQL，**回填缓存**，设置**随机 TTL**（防雪崩）。
   * 如果是热门商品且缓存刚好失效，触发**互斥重建**，只允许一个请求去查 DB，其余等待。
4. 返回商品信息。

**涉及的机制**：JWT 验证、限流（2）、精确缓存（L1）、互斥重建（22）、随机 TTL 防雪崩（22）。

### 第三阶段：用户咨询 AI 客服

**用户操作**：在聊天框输入问题。

**后端执行**：

1. 网关验证 JWT。
2. **限流器**检查 QPS。
3. **熔断器**检查下游 LLM 服务状态（如果连续失败 3 次，进入 OPEN 状态，直接返回降级答案，不调用 LLM）。
4. 请求进入 AI 客服 Agent：
   * **三级语义缓存查询**：L0（内存 LRU）→ L1（Redis 哈希）→ L2（PostgreSQL pg\_trgm 相似度 > 0.85）。命中则直接返回，**完全不调用 LLM**。
   * 未命中则进入 **RAG 双通道检索**：关键词（pg\_trgm）+ 向量（pgvector）双路召回 → DeepSeek Rerank 精排 → LLM 生成答案。
   * 生成过程中，**SSE 流式输出**逐字返回给前端。
   * 如果客户端断开连接，触发**断连取消**，终止 LLM 调用。
5. 答案生成完成后：
   * 回填 L0/L1/L2 缓存。
   * **冷热分层记忆**：热数据（最近对话）写入 Redis，冷数据通过 MQ 异步写入 PostgreSQL（**结构化日志 + 脱敏**记录整个流程）。
6. 返回答案给前端。

**涉及的机制**：JWT 验证、限流（2）、熔断（3）、三级语义缓存（6）、RAG 双通道（8）、SSE 流式（17）、断连取消（13）、冷热分层记忆（7）、消息队列（21）、结构化日志 + 脱敏（24）。

### 第四阶段：用户查询 / 修改个人信息

**用户操作**：查看或修改昵称、手机号、收货地址。

**后端执行**：

1. **查询**：
   * 读 Redis 缓存 `user:profile:{user_id}`，命中直接返回。
   * 未命中查 PostgreSQL，回填 Redis。
   * **慢查询监控**记录超过 100ms 的查询。
2. **修改**：
   * **乐观锁（版本号）**：`UPDATE users SET nickname = ?, version = version + 1 WHERE id = ? AND version = ?`。
   * 影响行数为 0 → 冲突 → 自动重试 3 次。
   * 修改成功后，删除 Redis 缓存（Cache Aside 模式）。
   * **结构化日志**记录修改操作，但**脱敏**（不记录手机号明文）。
3. 返回操作结果。

**涉及的机制**：JWT 验证、限流（2）、缓存 L1（6）、乐观锁（5）、慢查询监控（12）、结构化日志 + 脱敏（24）。

### 第五阶段：用户提交订单

**用户操作**：选择商品、填写收货地址，点击“提交订单”。

**后端执行**：

1. **幂等键检查**：前端请求头携带 `Idempotency-Key`（UUID）。后端查 Redis：`idem:{key}` 是否存在？存在则直接返回之前的订单结果（幂等返回）。
2. **开启数据库事务**（机制 16）：
   * 事务内执行：
     a. **乐观锁扣余额**：`UPDATE users SET balance = balance - amount, version = version + 1 WHERE id = ? AND version = ?`。
     b. **乐观锁扣库存**：类似版本号更新。
     c. 创建订单记录（`INSERT INTO orders ...`）。
     d. 插入 **WAL 流水**（`INSERT INTO transaction_wal ...`，只追加不修改）。
   * 任何一步失败 → 事务回滚 → 返回错误。
   * 全部成功 → 事务提交。
3. 事务提交后，写入 Redis 幂等键：`idem:{key} = order_result`，TTL 7 天。
4. 返回“订单创建成功”。

**涉及的机制**：幂等键（9）、数据库事务（16）、乐观锁（5）、WAL 流水（9）、重试机制（Bug #3 修复）。

### 第六阶段：用户支付

**用户操作**：选择支付方式，点击“确认支付”。

**后端执行**：

1. **分布式锁**：Redis `SET lock:order:{order_id} {token} NX EX 30`。获取失败 → 返回“订单正在处理中”。获取成功 → 启动**看门狗**（每 10 秒续期一次）。
2. **状态机校验**：确认订单状态是 `PENDING`。如果不是 → 幂等返回（已支付/已取消）。
3. **开启数据库事务**：
   * 调用第三方支付接口。
   * 支付成功后：`UPDATE orders SET status = 'PAID', version = version + 1 WHERE id = ? AND status = 'PENDING'`。
   * 更新 WAL 流水状态。
   * 事务提交。
4. 事务提交后：
   * **释放分布式锁**（Lua 脚本，校验 Token 后删除）。
   * **取消看门狗**。
   * 异步任务（通过 MQ）发送支付成功通知、更新缓存。
5. 返回“支付成功”。

**涉及的机制**：分布式锁 + 看门狗（4）、幂等状态机（9）、数据库事务（16）、WAL 流水（9）、消息队列（21）。

### 第七阶段：支付回调（外部渠道）

**外部触发**：支付宝/微信异步回调。

**后端执行**：

1. **验签**：验证回调签名，确认来自真实渠道。
2. **幂等检查**：查询订单状态，已经是 `PAID` → 直接返回成功。
3. **开启数据库事务**：更新订单状态 → 更新 WAL 流水 → 事务提交。
4. 返回 `200 OK`。

**涉及的机制**：验签（9）、幂等（9）、事务（16）、WAL 流水（9）。

### 第八阶段：后台异步与运维保障（并行运行）

**异步消费者（MQ Worker）**：

* 消费支付成功消息 → 发送邮件通知 → 更新缓存 → 触发后续任务（如积分增加）。
* 消费记忆落盘消息 → 写入 PostgreSQL（冷数据归档）。

**定时任务**：

* 超时未支付订单（30 分钟）→ 自动取消 → 释放库存。
* 冷热数据归档：7 天前的订单从 Redis 迁移到 PostgreSQL。

**监控与告警**：

* **SLO 告警**：错误率 > 5% 持续 1 分钟 → 钉钉/企微通知。
* **慢查询监控**：`pg_stat_statements` 捕获慢 SQL → 异常聚合告警。
* **日志检索**：通过 Loki + trace\_id 分钟级定位问题。

**发布与变更**：

* 代码变更 → CI/CD 滚动发布（4 实例逐个升级，健康检查通过才继续）。
* 数据库变更 → Alembic 版本化迁移（可 `upgrade` / `downgrade`）。
* 配置变更 → 环境变量注入（不写死代码）。

**数据保护**：

* 每日全量备份 + WAL 实时归档 → 支持 PITR 时间点恢复。
* 延迟从库 → 快速应对误操作（如误删表）。

**涉及的机制**：消息队列消费（21）、冷热分层归档（7）、SLO 告警（12）、慢查询监控（12）、滚动发布（10）、数据库迁移（11）、配置管理（23）、备份与恢复（16）。

# 第七部分：面试问答精选

## 架构与设计

1. **为什么用网关架构？** 所有流量必经 → 认证/限流/熔断/计费/观测有统一落点；业务与基建解耦。
2. **一核双用怎么实现的？** 引擎只管调度与输出；人设/工具/模型策略外置配置包；新增领域=新增配置包。
3. **JWT 为什么能多实例共享？** 无状态，验签即验真，不依赖会话存储。
4. **简单/复杂任务为什么分路？** 省 token（钱）+ 省延迟；简单问题不为复杂流程空转。

## 并发与一致性

5. **分布式锁和乐观锁的区别？** 分布式锁管"进门"（业务层），乐观锁管"数据版本"（数据层），双保险。
6. **分布式锁的坑？** 锁过期、不可重入、主从切换丢锁；解决：看门狗续期、可重入锁、Redlock。
7. **乐观锁什么时候重试会失败？** 高冲突场景（同一行频繁改）；此时用悲观锁/队列。
8. **为什么扣费必须检查版本冲突？** 不检查 = 余额没更新但流水照记 = 账目错误。
9. **幂等怎么保证？** 状态机 + 幂等键 + 唯一约束 + 分布式锁。
10. **WAL 是什么？** 只追加的流水表 = 真相，可对账、不可篡改。

## 缓存与数据

11. **三级缓存为什么这样分？** 速度 × 成本平衡；命中逐级回填越用越快。
12. **缓存穿透/击穿/雪崩？** 穿透存空值；击穿互斥重建；雪崩随机过期。
13. **为什么语义缓存阈值 0.85？** 宁可不命中，不能给错答案。
14. **冷热分层记忆为什么异步写？** 同步写 PG 拖慢主流程；异步 + 信号量限流。
15. **索引类型怎么选？** 范围用 B-tree，模糊/包含用 GIN，向量用 ivfflat。

## AI / Agent

16. **ReAct 循环是什么？** 思考-行动-观察：想该干嘛 → 调工具 → 看结果 → 再想。
17. **多 Agent 为什么比单 Agent 好？** 单 Agent 漏领域；多 Agent 交叉补全。
18. **RAG 为什么双通道？** 关键词补术语、向量补语义；召回求全、精排求准。
19. **Rerank 为什么只精排 top_k？** 全量精排太贵；两段式控质量与成本。
20. **温度参数怎么用？** 分类/法律用 0，日常 0.3，创意 1；法律要严谨。

## 运维与工程化

21. **滚动发布为什么不停机？** 一次只升级一个实例，健康才动下一个。
22. **失败怎么回滚？** 发布前记录镜像，失败 tag 回旧镜像重启。
23. **数据库迁移为什么必须版本化？** 结构变更可追溯可回滚；防线上库与代码对不上。
24. **SLO 怎么定？** SLI（测什么）→ 目标数字（<1% 错误率）→ 告警 → 处置 SOP。
25. **慢查询为什么危险？** 占连接池 → 连接耗尽 → 全站变慢；要 pg_stat_statements 监控。
